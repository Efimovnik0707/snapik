# SnapBrief для macOS — спецификация порта 1:1

Источник истины: работающая Windows-сборка SnapBrief (C# / WPF / .NET 10), исходники в `src/`, тесты в `tests/`.
Задача: воспроизвести поведение на Swift + AppKit + ScreenCaptureKit, macOS 14+ (Sonoma), без чтения C#-кода.

Ссылки вида `Файл.cs:12` указывают строку в Windows-исходнике как доказательство утверждения.
Читать C# не нужно: всё поведение описано здесь текстом.

Язык интерфейса: русский (по умолчанию) и английский. Контекст пользователя — EU/Spain.
Данные и снимки остаются локальными: нет сети, API-ключей, телеметрии, облака (`PRODUCT.md:42`).

## 1. Обзор поведения

### 1.1 Запуск и покой

1. Приложение стартует **без видимого окна**. На Windows это трей; окно стопки создаётся, но сразу
   скрывается на первом Loaded (`EdgeStackWindow.xaml.cs:123` — `Hide()` внутри `OnLoaded`).
   `README.md:42`: «При запуске SnapBrief работает в трее без открытой панели».
2. Иконка в трее с тултипом `SnapBrief` (`EdgeStackWindow.xaml.cs:76-82`).
3. Контекстное меню трея (порядок пунктов, `EdgeStackWindow.xaml.cs:83-89`):
   1. **Показать стопку**
   2. **Настройки** — показывает стопку и открывает окно настроек
   3. **Новый снимок**
   4. *(разделитель)*
   5. **Выйти** — реально завершает процесс
   6. **Запускать с Windows** — переключатель автозапуска (галочка)
4. Двойной клик по иконке трея = «Показать стопку» (`EdgeStackWindow.xaml.cs:109`).
5. При открытии меню все пункты переводятся на текущий язык, а состояние галочки автозапуска
   перечитывается из системы; при ошибке чтения пункт отключается (`:90-95`).
6. Стопка **не Topmost** (`EdgeStackWindow.xaml:7`). Таймера автоскрытия нет
   (`tasks/verification.md:86`: «Удалены таймер четырёх секунд и отложенный Deactivated-hide»).

**macOS:** `NSApplication` с `LSUIElement = true` в Info.plist (нет иконки в Dock), `NSStatusItem`
в menu bar с `NSMenu` тех же шести пунктов. Двойной клик по status item в macOS не различается —
одиночный левый клик = «Показать стопку», правый / Control-клик открывает меню. См. §9.

### 1.2 Горячая клавиша захвата и выделение области

1. Дефолт захвата: **Ctrl+Alt+S** (`HotkeySettingsWindow.xaml.cs:28`, `:31` — модификаторы
   Control+Alt+NoRepeat, виртуальная клавиша `0x53` = `S`). На macOS: **Command+Option+S**, см. §7.
2. Нажатие клавиши:
   - Если оверлей уже открыт и в нём есть снимок — текущий снимок **коммитится** и сразу
     начинается следующий захват, без отдельного «Готово» (`EdgeStackWindow.xaml.cs:175`,
     `OverlayEditorWindow.xaml.cs:97-103`). Коммит **не** происходит, если идёт обрезка,
     тянется угол снимка или холст держит мышь.
   - Иначе запускается цикл захвата (`EdgeStackWindow.xaml.cs:234`).
3. Цикл захвата:
   - Ждёт незавершённый переход сессии после вставки (`:236`).
   - Защита от повторного входа: флаг занятости (`:237-238`).
   - Проверяет, надо ли начать новую сессию (§1.12).
   - Скрывает **все** окна SnapBrief кроме оверлея, прокачивает очередь отрисовки
     и вызывает `DwmFlush()`, чтобы свои окна гарантированно исчезли до снятия кадра (`:326-332`).
   - Ждёт 120 мс (`OverlayEditorWindow.xaml.cs:79`), снимает кадр всего виртуального рабочего стола
     и открывает оверлей.
4. **Кадр рабочего стола** (`CaptureOverlay.xaml.cs:60-85`): прямоугольник виртуального экрана из
   `GetSystemMetrics(76, 77, 78, 79)` = SM_XVIRTUALSCREEN, SM_YVIRTUALSCREEN, SM_CXVIRTUALSCREEN,
   SM_CYVIRTUALSCREEN; копия через `CopyFromScreen`. Курсор дорисовывается только при включённой
   настройке «Захватывать курсор» (§1.16), с учётом hotspot (`CaptureCursorDrawing.cs:20`).
   Структура кадра: `DesktopFrame(Image, Left, Top, PixelWidth, PixelHeight)` (`CaptureOverlay.xaml.cs:178`).
5. Оверлей — **полноэкранное непрозрачное окно** поверх всего (`OverlayEditorWindow.xaml:6-7`:
   без системной рамки, без per-pixel прозрачности, фон `#0A0D12`, поверх всех окон,
   не в панели задач, курсор-перекрестие). Оно показывает **замороженный** снимок рабочего стола
   как обычную картинку и позиционируется ровно по кадру (`OverlayEditorWindow.xaml.cs:144-148`).
   Отказ от per-pixel transparency — осознанное решение по производительности
   (`tasks/verification.md:67`), повторить его.
6. Изначально виден только подсказочный чип по центру сверху: **«Выделите область · Esc отменяет»**
   (`OverlayEditorWindow.xaml:65-68`). Чип: фон `#E8171A20`, padding 13,8, скругление 10,
   текст белый 13 pt, отступ сверху 24.
7. Пользователь **протягивает прямоугольник левой кнопкой**. Затемнение — заливка `#A20A0D12`
   с even-odd дыркой под выделением (`OverlayEditorWindow.xaml:43`, `:274-278`).
8. Отпускание мыши:
   - Если прямоугольник меньше **12x12 DIP** по любой стороне — выделение сбрасывается, оверлей
     остаётся в режиме выбора (`OverlayEditorWindow.xaml.cs:199`).
   - Иначе координаты DIP пересчитываются в пиксели кадра множителем
     `frame.PixelWidth / ActualWidth`, зажимаются в границы кадра, делается вырезка (`:203-212`).
   - Полученный PNG немедленно сохраняется на диск как исходник снимка (§3.4), после чего
     включается редактор разметки.
   - Повторный вход во время сохранения заблокирован флагом (`:202`, `tasks/verification.md:67`).
9. **Esc** до выделения — оверлей закрывается, сессия не меняется (`:737-742`).

**macOS:** ScreenCaptureKit — `SCShareableContent` в `SCDisplay` для каждого экрана,
`SCScreenshotManager.captureImage` (macOS 14+). Нужно TCC **Screen Recording**, см. §9.1.
`GetSystemMetrics(76..79)` соответствует объединению `NSScreen.screens[i].frame`; на macOS начало
координат — левый-нижний угол главного экрана, ось Y вверх, нужен явный флип (§9.5).

### 1.3 Разметка

После выделения области оверлей переходит в режим разметки (`SetupEditor`, `OverlayEditorWindow.xaml.cs:228-257`):

- Синяя рамка `#2F8CFF` толщиной 2 вокруг снимка (`OverlayEditorWindow.xaml:45`).
- Внутри рамки — холст разметки `AnnotationCanvas` (§6.3) с `ImagePadding = 0`.
- Активный инструмент по умолчанию — **Rectangle (Область)** (`OverlayEditorWindow.xaml.cs:239`,
  `OverlayEditorWindow.xaml:92`).
- Активный цвет — первый в палитре `#2F8CFF` (RGB 47,140,255) (`OverlayEditorWindow.xaml.cs:26-32`, `:240`).
- Активная толщина — **4** (индекс 1 в массиве `[3, 4, 6, 9]`, `:51-53`, `:241`).
- Появляется плавающая панель инструментов (§6.2) и четыре угловые ручки снимка (§1.6).
- Подсказка скрывается; комментарий к снимку скрыт, его поле заполнено текущей заметкой,
  заголовок поля становится `СНИМОК {метка}` (`:242-246`).

#### Дополнение 2026-09-09: палитра и толщина

Заменяет цикличное переключение выше: кнопка «•••» больше не содержит пунктов «Цвет отметки»/
«Толщина» и разделителя перед ними (`OverlayEditorWindow.xaml.cs:317-321` в исходной версии, до
правки) — остаются только Перо/Маркер/Текст/Скрыть сплошным, без разделителя, с отметкой текущего
инструмента (`state`/`IsChecked`); кнопка «•••» дополнительно подсвечивается, когда активен один из
этих четырёх инструментов, и её тултип показывает какой именно (`OverlayEditorWindow.Appearance.cs:65-67`).

Вместо цикла — видимая кнопка «Цвет и толщина» на основной панели (кружок текущего цвета + `{N} px`,
между Crop и «•••»), открывающая popover (§6.2). Активный цвет/толщина хранятся напрямую
(`_activeColor`/`_activeThickness`, не индексом в массиве). `HasColor(tool)` — Rectangle, Arrow,
Pen, Highlight, Text; `HasStroke(tool)` — то же самое кроме Text. Кнопка недоступна (opacity 0.4,
клик игнорируется), если у активного инструмента (или выделенной отметки) нет цвета вовсе — Select,
Blur, Crop, Conceal; внутри popover от `HasStroke` зависит только ползунок толщины и линия примера
(скрыта при отключённой толщине), сама палитра и поле HEX не блокируются отдельно.

Выбор в palette/HEX/ползунке применяется немедленно: если есть выделенная отметка — меняется её
цвет/толщина и подсвечивается сама отметка; независимо от выделения обновляется активное
значение по умолчанию для следующих новых отметок. Все правки за одно открытие popover (от открытия
до закрытия любым способом — крестик, Esc, клик снаружи) сворачиваются в одну запись истории: при
открытии запоминается снимок «до», при закрытии, если что-то реально изменилось, он пушится в Undo
одним элементом. Поле HEX принимает `#RGB`/`#RRGGBB`/`#AARRGGBB` (шире, чем 6-значный формат
Windows-поля, ограниченного `MaxLength="7"`); при ошибке разбора граница поля подсвечивается
красным до следующего успешного применения.

#### Порог создания отметки

Отметка добавляется только если жест имеет размер (`AnnotationCanvas.cs:417-422`):
- Pen / Highlight: **больше двух** точек в полилинии;
- остальные: расстояние между первой и второй точкой **не меньше 3 пикселей изображения**.

Иначе черновик отбрасывается без записи в историю.

#### Crop как отдельный случай

Если активен инструмент Crop, по отпускании вместо создания отметки вызывается обрезка снимка
(`AnnotationCanvas.cs:221-222`, `OverlayEditorWindow.xaml.cs:668`). Минимальный размер обрезки —
**8x8 пикселей изображения** (`:677`). После обрезки инструмент автоматически переключается на Select
(`:704-706`).

### 1.4 Комментарии

Правило пользователя (`PRODUCT.md:68`, `tasks/prd-snapbrief.md:438`):
после **начального захвата** поле комментария **не** открывается автоматически;
после рисования **рамки (Rectangle)** поле появляется автоматически рядом с этой рамкой и получает
фокус; для остальных отметок и для комментария ко всему снимку есть компактная контекстная кнопка;
крестик удаляет **только заметку**, отметка остаётся.

Реализация (`OverlayEditorWindow.xaml.cs:339-352`): при создании отметки пишется история; если вид
Rectangle — идентификатор добавляется в множество видимых чипов, создаётся чип-комментарий
**с фокусом и выделенным текстом**, контекстная кнопка скрывается. Для всех остальных видов —
показывается контекстная кнопка возле геометрии.

#### Чип комментария к отметке (`AddChip`, `OverlayEditorWindow.xaml.cs:391-434`)

Контейнер: ширина **226**, минимальная высота **40**, padding **6**, скругление **13**,
фон ARGB(244,23,26,32), тень чёрная blur 14, смещение 4, opacity 0.42.
Внутри сетка из трёх колонок `31 | * | 29`:
1. Круглый бейдж 25x25, радиус 13, фон `#2F8CFF`, белый жирный текст 11 pt — номер отметки (`A1`, `B2`).
2. Текстовое поле: MinHeight 32, MaxHeight 78, многострочное, перенос слов, прозрачный фон,
   белый текст, без рамки, каретка белая, выделение `#2F8CFF`, padding 7,5,7,5.
3. Кнопка-крестик 27x27, padding 7, прозрачная, путь `M1,1 L9,9 M9,1 L1,9`, обводка `#D9DEE8`,
   толщина 1.5, скруглённые концы, тултип «Удалить комментарий».

Ввод текста немедленно пишется в заметку отметки и перерисовывает подписи (`:402`).
Фокус в поле выделяет соответствующую отметку на холсте (`:403`).
Требование `.impeccable/surfaces/src-snapbrief-app-overlayeditorwindow-xaml.md:33`: набор текста
**обязан** сохранять фокус, каретку и состояние IME; поле нельзя пересоздавать на каждое нажатие.

**Позиционирование чипа** (`PositionChip`, `:459-470`):

```
x = cropRect.Left + bounds.Left
y = cropRect.Top  + bounds.Bottom + 8                             // под отметкой
если y + 86 > work.Bottom:  y = cropRect.Top + bounds.Top - 50    // над отметкой
x = clamp(x, work.Left + 8, max(work.Left + 8, work.Right  - 230))
y = clamp(y, work.Top  + 8, max(work.Top  + 8, work.Bottom - 88))
```

`work` — рабочая область того монитора, в центре которого находится снимок
(`GetCropMonitorWorkArea`, `:598-611`); она пересчитывается из экранных пикселей в координаты окна
оверлея через масштаб `frame.PixelWidth / ActualWidth`.

#### Крестик у чипа (`OnDeleteAnnotationNoteClick`, `:565-579`)

Если заметка непустая — состояние кладётся в undo. Заметка очищается, redo очищается,
чип удаляется из слоя, **отметка остаётся на изображении**, подписи перенумеровываются,
панель инструментов перепозиционируется, контекстная кнопка снова показывается.

#### Контекстная кнопка комментария (`ContextNoteButton`, `OverlayEditorWindow.xaml:54-62`)

Кнопка 32x32, padding 8, фон `#F2171A20`, рамка `#46515F`, иконка облачка
(`M2,2 L13,2 L13,10 L7,10 L4,13 L4,10 L2,10 Z`, обводка `#EEF2F8`, толщина 1.6)
с синей точкой-индикатором `#2F8CFF` 6x6 в правом верхнем углу, тултип «Добавить комментарий».

Позиционирование (`UpdateContextNoteAffordance`, `:533-563`):

```
если есть выделенная отметка и её чип не открыт:
    x = cropRect.Left + bounds.Right + 8
    y = cropRect.Top  + bounds.Top   - 4
    если x + 36 > work.Right:  x = cropRect.Left + bounds.Left - 40
иначе:
    x = cropRect.Right - 40
    y = cropRect.Top   + 8
x = clamp(x, work.Left + 8, max(work.Left + 8, work.Right  - 40))
y = clamp(y, work.Top  + 8, max(work.Top  + 8, work.Bottom - 40))
```

Кнопка скрывается, если у выделенной отметки уже открыт чип.

Клик по кнопке (`OnCommentClick`, `:513-531`):
- есть выделенная отметка — открыть её чип или сфокусировать существующий;

### 1.5 Undo / Redo в оверлее

Локальная история оверлея (не `SessionHistory` из Core) — два стека снимков состояния
(`OverlayEditorWindow.xaml.cs:38-39`, `:621-666`).

Единица истории — `OverlaySnapshot(Capture, CropRect, VisibleChipIds, ShotNoteVisible)` (`:794`),
где `Capture` = глубокая копия снимка: идентификатор, изображение, путь исходника, метка,
заметка снимка и **клоны всех отметок** (`EditorModels.cs:158`, `:200`).

В историю попадают:
- создание отметки (`:342`);
- перемещение или изменение размера отметки (`:363`);
- удаление отметки клавишей Delete (через событие изменения, `AnnotationCanvas.cs:243`);
- удаление заметки крестиком чипа (`:568`);
- удаление комментария к снимку (`:584`);
- обрезка снимка (`:701`);
- изменение границ снимка за угол (`OverlayEditorWindow.Resize.cs:177`).

Изменение **текста** заметки историю не пушит, но очищает redo и обновляет последнее состояние
(`:376-378`, `:617-618`): отменить набор текста нельзя, но новая правка не воскресит redo.

Undo и Redo блокируются, если идёт обрезка или тянется угол снимка (`:629-641`).
Восстановление (`:645-666`) возвращает: пиксели, путь исходника, метку, заметку, все отметки,
прямоугольник снимка, набор видимых чипов, видимость комментария к снимку; затем перестраивает
чипы, контекстную кнопку, панель, позицию комментария и перерисовывает холст.

Горячие клавиши: **Ctrl+Z** и **Ctrl+Y** (`:744-745`). На macOS: **Command+Z** и **Shift+Command+Z**
(§7.4). Кнопки «Отменить» и «Повторить» на панели — стрелки.

### 1.6 Изменение границ снимка за четыре угла

Требование пользователя: `PRODUCT.md:73`, `tasks/prd-snapbrief.md:448`.

- Четыре ручки по углам прямоугольника снимка: hit-target **22x22 DIP**, визуальный маркер
  внутри — белый квадрат **8x8** с рамкой `#2F8CFF` толщиной 1.5 и скруглением 2
  (`OverlayEditorWindow.Resize.cs:58-101`). Курсоры: углы 0 и 2 диагональ NWSE, углы 1 и 3 NESW.
  Имена для доступности: `Угол снимка 1..4`, тултип `Изменить границы снимка`.
- Нумерация углов **по часовой стрелке**: `0 = TopLeft, 1 = TopRight, 2 = BottomRight, 3 = BottomLeft`
  (`Controls/ResizeGeometry.cs:9`).
- Ручки позиционируются как `corner - 11` по обеим осям и зажимаются в границы окна оверлея
  (`Resize.cs:117-118`).
- Во время перетаскивания показывается контурная рамка `#2F8CFF` толщиной 2 и обновляется затемнение;
  фактическая обрезка или расширение **не** выполняется до отпускания (`Resize.cs:90-96`).
- Минимальный размер при изменении границ снимка — **12 DIP** (`Resize.cs:93`).
- **Расширение использует только уже захваченные пиксели** (`Resize.cs:107-111`): источник —
  замороженный кадр рабочего стола для нового снимка либо сохранённое изображение снимка при
  повторном открытии. Новое содержимое экрана при расширении не захватывается.
- После отпускания (`Resize.cs:126-139`): если drag отменён или прямоугольник не изменился —
  вернуть визуал; иначе применить.
- Применение (`Resize.cs:140-190`):
  1. Пересчитать запрошенный DIP-прямоугольник в пиксели источника, зажать, взять вырезку.
  2. Сохранить производное изображение на диск (§3.4) и запомнить путь как временный.
  3. Клонировать снимок и **перевести координаты всех отметок, включая все сегменты полилиний,
     в систему источника**:

     ```
     sx = source.PixelWidth  / sourceRect.Width
     sy = source.PixelHeight / sourceRect.Height
     scaleX = cropRect.Width  * sx / capture.PixelWidth
     scaleY = cropRect.Height * sy / capture.PixelHeight
     offset = ((cropRect.Left - sourceRect.Left) * sx, (cropRect.Top - sourceRect.Top) * sy)
     p -> (p.x * scaleX, p.y * scaleY) + offset
     ```
  4. Выполнить `CaptureCropper.Crop` (§2.7) в нормализованных координатах источника.
  5. Заменить снимок, сохранить метку и выделение, пересчитать прямоугольник снимка, положить
     прежнее состояние в undo, очистить redo, пересобрать редактор и чипы, обновить затемнение.
  6. При ошибке — откат к предыдущему состоянию и подсказка `Не удалось изменить границы снимка: {ошибка}`.
- Сужение снимка **обрезает выходящие за границы отметки** (это делает `CaptureCropper`), Undo
  восстанавливает предыдущее состояние.
- Экспорт **не коммитится** во время активного перетаскивания (`tasks/verification.md:69`).

Угол **отметки** (не снимка) можно тянуть **при любом активном инструменте**
(`AnnotationCanvas.cs:300-315`): выделенная отметка владеет перекрывающимися ручками;
радиус попадания по углу отметки — **10 DIP**. Приоритет: сперва выделенная отметка, затем все
остальные в обратном порядке добавления. Минимум при изменении размера отметки — **2 пикселя
изображения** (`AnnotationCanvas.cs:164-165`), лимит — прямоугольник изображения.

### 1.7 Размытие: превью и коммит

- При **рисовании новой** области blur (до отпускания мыши) виден полупрозрачный белый заливной
  прямоугольник ARGB(54,255,255,255) с синей рамкой `#2F8CFF` толщиной 1.5
  (`AnnotationCanvas.cs:360-362`). Финальное размытие применяется после завершения жеста
  (`PRODUCT.md:74`). Исключение blur из отрисовки черновика было удалено
  (`tasks/verification.md:78`), поэтому превью **обязано** быть видимым — это проверяется smoke-тестом
  сравнением пикселей холста до и во время жеста.
- При **перемещении или изменении** существующей blur-области рисуется **сплошная чёрная маска**
  с синим контуром (`AnnotationCanvas.cs:109-110`), размытие пересчитывается только после
  отпускания (`PRODUCT.md:73`). Во время манипуляции используется прежний raster-кэш (`:443`).
- Кэш размытия ключуется по хэшу от identity исходного bitmap плюс (id, thickness, все точки)
  каждой blur-отметки (`AnnotationCanvas.cs:444-453`).
- Радиус размытия: `clamp(round(thickness * 3), 4, 36)` (`AnnotationCanvas.cs:463`, дублируется в
  экспорте `WpfExportImageRenderer.cs:77`). При дефолтной толщине 4 радиус равен 12.

### 1.8 Завершение снимка

Снимок сворачивается в стопку любым из этих действий:

| Действие | Код | Эффект |
|---|---|---|
| Клик **вне снимка** по затемнённому фону | `OverlayEditorWindow.xaml.cs:184-193` | снимок в стопку, оверлей закрывается |
| **Ctrl+C** вне текстового поля | `:746` | то же самое |
| Кнопка **«Готово»** | `:716` | то же самое |
| Кнопка **«+ Снимок»** | `:717` | снимок в стопку и **сразу** новый захват |
| Повторное нажатие горячей клавиши захвата | `:97-103` | снимок в стопку и сразу новый захват |

Условия клика по фону (`:188`): есть снимок, источник события — сам образ рабочего стола,
не идёт обрезка, точка **вне** прямоугольника снимка. Событие помечается обработанным —
клик **не** проходит в нижележащее приложение (FR-20, `tasks/prd-snapbrief.md:162`).

Ctrl+C **внутри** текстового поля работает как обычное копирование текста: обработчик клавиш
проверяет, что фокус в текстовом поле, и выходит (`:732-736`); внутри поля Escape просто снимает
фокус на холст.

Коммит (`:719-727`):
1. Запомнить область (если включена настройка «Запоминать последнюю область» и снимок новый).
2. Скопировать текст поля комментария снимка в модель.
3. **Удалить все созданные за сессию редактирования временные исходники, кроме финального**
   (`DeleteCreatedSourcesExcept`, `:780-789`) — промежуточные обрезки не остаются мусором.
   Удаление ограничено каталогом сессии (проверка префикса пути).
4. Вернуть результат `(capture, addNext, cancelled = false)`.

Блокировки коммита: нет снимка, идёт обрезка, тянется угол, холст держит мышь (`:721`).

**После возврата** в цикл захвата (`EdgeStackWindow.xaml.cs:246-252`):
1. Снимок добавляется в список.
2. Перенумерация: метки A, B, C по позиции.
3. Подготовленный экспорт инвалидируется.
4. **Сохранение и копирование пакета** (§1.10).
5. Если копирование прошло и был запрошен следующий снимок — цикл повторяется.
6. В любом случае стопка показывается без активации.

При отмене (Esc) в редакторе существующего снимка возвращается неизменённый снимок с флагом
отмены, и стопка **не** меняется (`:739-741`, `:300`).

  (`tasks/verification.md:21`).

### 1.10 Пакет в буфере обмена

После **каждого** завершения снимка (`SaveAndCopyCommittedPackageAsync`, `EdgeStackWindow.xaml.cs:386-404`):

1. Подготовка: сохранить сессию и собрать новый неизменяемый revision (§4).
2. Прочитать текущее состояние буфера и получить его номер последовательности.
3. **Guarded-запись** пакета: если номер не совпал с ожидаемым — исключение, буфер не трогается.
4. Запомнить receipt (номер последовательности **после** записи) и текст текущего пакета —
   это доказательство владения буфером.
5. Показать уведомление **«Снимки скопированы»** (если включены уведомления).
6. Сбросить строку статуса.
7. При ошибке: сохранить сессию и показать статус
   **«Снимок сохранён, но буфер не обновлён: {ошибка}. Повторите копирование через меню.»**,
   вернуть неуспех — цикл «+ Снимок» прерывается.

Что кладётся в буфер (`WindowsClipboardService.CreatePackageDataObject`, `WindowsClipboardService.cs:198-213`):

- **один снимок** — формат `PNG` (сырые байты файла), `CF_DIB`, `CF_BITMAP` (авто-конвертируемый),
  **плюс** список файлов `CF_HDROP` из одного пути, **плюс** `CF_UNICODETEXT` с текстом задания;
- **несколько снимков** — **только** упорядоченный `CF_HDROP` со всеми путями и `CF_UNICODETEXT`.
  Комментарий в коде (`:204-206`): у Windows нет стандартного формата для нескольких независимых
  изображений, поэтому мульти-пакет — это список файлов.

Это закреплено тестами (§8: `SingleImagePackage_…`, `MultiImagePackage_…`, `tasks/verification.md:32`).

### 1.11 Детект вставки и ротация сессии

**Наблюдение намерения вставки** (`WindowsPasteIntentObserver`): низкоуровневый клавиатурный хук
`WH_KEYBOARD_LL` слушает **все** нажатия в системе (`WindowsPasteIntentObserver.cs:37`) и распознаёт
**Ctrl+V** или **Alt+V** (`PasteIntentKeyState.Observe`, `:161-196`). Правила:

- инъецированные события (флаг `LLKHF_INJECTED = 0x10`) игнорируются — SnapBrief не реагирует
  на собственные нажатия;
- модификаторы отслеживаются множествами: Ctrl (`0x11`, `0xA2`, `0xA3`),
  Alt (`0x12`, `0xA4`, `0xA5`), прочие (Shift `0x10`, `0xA0`, `0xA1`; Win `0x5B`, `0x5C`);
- гест выдаётся только на **первое** нажатие `V` (`0x56`); авто-повтор гасится флагом «V уже нажата»;
  требуется **ровно один** из Ctrl и Alt (если оба нажаты или оба нет — игнор, значит AltGr тоже игнор)
  и **отсутствие** прочих модификаторов;
- событие несёт: гест, дескриптор переднего окна, идентификатор процесса переднего окна,
  **номер последовательности буфера** и UTC-время (`:67-72`);
- события от **собственного процесса** отбрасываются (`:65`);
- исключения внутри хука никогда не выходят наружу (`:77-80`);
- хук создаётся, стартует, останавливается и освобождается **только на своём UI-потоке** (`:92-96`).

**Реакция** (`OnPasteIntentObserved`, `EdgeStackWindow.xaml.cs:179-192`):
1. Если у SnapBrief нет собственного пакета в буфере или номер последовательности в событии
   не равен номеру нашего пакета — **игнор**, вставляли не наше.
2. Если пакет наш, но текста нет — статус
   **«Не удалось подтвердить содержимое текущего пакета. Сессия сохранена.»**
3. Если уже идёт ротация или прошлый переход не завершён — игнор.
4. Иначе запускается завершение вставки.

Завершение вставки (`:194-230`):
- Вызывает Codex-догон текста (§5.4).
- Если за время ожидания появился **новый** пакет — ничего не ротировать (защита от ротации новой
  сессии по старому намерению, комментарий `:204-205`).
- Если догон записал текст в буфер — обновить наш receipt на новый.
- Статус `CompletedUnverified` — **начать новую сессию**.
- Статус `NotApplicable` (вставляли не в Codex Desktop) — если наш пакет всё ещё в буфере,
  **всё равно начать новую сессию**: пользователь вставил наш пакет куда-то ещё.
- Прочие статусы — **«Снимки сохранены, но вставка текста не завершена: {сообщение}»**.
- Исключение — **«Вставка замечена, но новая сессия не создана: {ошибка}»**.

**Ротация сессии** (`StartNewSessionAsync`, `:616-648`):
1. Флаг сброса, остановка debounce-таймера, взятие мьютекса мутаций.
2. `SessionWorkspace.StartNewSessionAsync` (`SessionWorkspace.cs:108-124`):
   сохранить текущую сессию, создать **новую пустую** сессию, **сразу записать её на диск**
   и перевести указатель `current-session.txt` на неё. Прошлая сессия и её файлы **остаются**.
3. Очистить список снимков, **скрыть стопку**, сбросить legacy-заметку, стек удалённых,
   подготовленный экспорт, владение буфером; перенумеровать; очистить статус.
4. Ошибка — статус **«Не удалось начать новую сессию: {ошибка}»**.

### 1.12 Поведение при чужом копировании

Перед каждым захватом (`EnsureCurrentCaptureSessionAsync`, `:263-285`):
- если снимков нет — продолжать в текущей сессии;
- если у нас есть receipt и буфер **всё ещё наш** — продолжать в текущей сессии;
- иначе (пакет вставлен, заменён или это перезапуск приложения) — сбросить владение и **начать новую
  пустую сессию**; прежние файлы сохранены на диске;
- чужой буфер **не затирается**, пока новый снимок не завершён (`:272-274`, `tasks/prd-snapbrief.md:442`);
- ошибка проверки — статус **«Не удалось проверить буфер перед новым снимком: {ошибка}»**,
  захват **не** начинается.

Похожая логика при любом изменении стопки (`RefreshOwnedClipboardAsync`, `:656-688`):
- буфер уже не наш — просто забыть о владении;
- снимков не осталось — записать **пустой текст** в буфер (чтобы удалённые снимки не остались
  доступны для вставки) и сбросить подготовку;
- иначе — пересобрать экспорт и перезаписать пакет, уведомить о копировании;
- «буфер изменён» — тихо сбросить владение;
- прочая ошибка — статус **«Сессия сохранена, но буфер не обновлён: {ошибка}»**.

### 1.13 Сохранение снимка в файл (Ctrl+S, на macOS Command+S)

Кнопка-дискета на панели разметки и **Ctrl+S** (`OverlayEditorWindow.Save.cs:14-43`,
привязка клавиши `OverlayEditorWindow.xaml.cs:731`).

1. Блокируется, если нет снимка, идёт обрезка, тянется угол или холст держит мышь.
2. Диалог сохранения:
   - заголовок — локализованный `Сохранить на компьютер (Ctrl+S)`;
   - фильтр `PNG (*.png)|*.png|JPEG (*.jpg;*.jpeg)|*.jpg;*.jpeg`;
   - предвыбранный фильтр и расширение — из настройки «Формат»;
   - имя файла по умолчанию — `SnapBrief-yyyy-MM-dd-HHmmss-fff-XXXX`, где XXXX — 4 hex-символа
     нового GUID (`LocalImageSave.cs:27-28`);
   - стартовая папка — «Папка сохранения» из настроек, если существует, иначе Изображения пользователя;
   - предупреждение о перезаписи включено.
3. На время диалога Topmost снимается и восстанавливается после (`Save.cs:32`, `:42`).
4. **Отмена диалога не завершает снимок** — редактор и разметка остаются (`README.md:48`).
5. Формат определяется по фактическому расширению выбранного файла (`.jpg` или `.jpeg` в JPEG,
   иначе PNG); другое расширение — ошибка **«Выберите PNG или JPEG.»**
6. Сохраняется **изображение с разметкой** (§4.4), а не исходник.
7. Запись атомарна (`LocalImageSave.WriteAsync`, `LocalImageSave.cs:10-26`): сначала полное
   кодирование в память в фоновом потоке, затем запись во временный файл `путь.{guid}.tmp`,
   затем перемещение с перезаписью; временный файл удаляется в блоке finally.
   **Существующий файл не трогается, пока новый не закодирован полностью.**
8. Качество JPEG — из настроек, зажимается в диапазон 1..100.
9. После успеха — запомнить область (если включено) и показать уведомление **«Снимок сохранён»**.
10. Ошибка — текст ошибки в подсказочном чипе оверлея.

Сохранение файла **не меняет** пакет в буфере (`README.md:48`).

### 1.14 Быстрое сохранение всего рабочего стола

Отдельная, **по умолчанию выключенная** команда (`HotkeySettingsWindow.xaml.cs:17`).
Сочетание по умолчанию — идентификатор `custom:4:44` (`:18`), то есть модификатор Shift (флаг 4)
плюс виртуальная клавиша `0x2C` (44) — **Shift+Print Screen**.

Работа (`EdgeStackWindow.Saving.cs:16-32`):
1. Дождаться незавершённого перехода, проверить занятость, запомнить видимость стопки.
2. Скрыть все окна SnapBrief, подождать 120 мс.
3. Снять кадр **всего виртуального рабочего стола** (с курсором, если включено).
4. Записать в файл в выбранную папку, в выбранном формате и качестве, **без перезаписи**.
5. Уведомление **«Снимок сохранён»**.
6. Ошибка — статус **«Не удалось сохранить экран: {ошибка}»**, стопка обязательно показывается.

Эта команда **не добавляет** изображение в текущий пакет и **не заменяет** буфер (`README.md:50`).

### 1.16 Запоминание области

Настройка «Запоминать последнюю область» (по умолчанию **выключена**, `HotkeySettingsWindow.xaml.cs:20`).

Сохранение (`RememberCurrentRegion`, `Save.cs:47-59`) — только для **нового** снимка, при включённой
настройке и непустом прямоугольнике. Файл `last-region.json` рядом с `settings.json`
(`SessionWorkspace.cs:41`), формат:

```json
{"Left":0,"Top":0,"Width":3840,"Height":2160,"X":0.25,"Y":0.3,"W":0.4,"H":0.35}
```

`Left/Top/Width/Height` — геометрия виртуального рабочего стола в пикселях,
`X/Y/W/H` — доли от размера окна оверлея. **Имена полей в PascalCase** — это отдельный сериализатор
с настройками по умолчанию, не общий `SnapBriefJson`. Ошибки записи глотаются.

Восстановление (`RestoreLastRegion`, `Save.cs:61-83`) применяется **только** если сохранённая
конфигурация мониторов **точно совпадает** с текущей (равны `Left`, `Top`, `Width`, `Height`),
доли конечны, положительны и `X + W <= 1.00001`, `Y + H <= 1.00001`. Иначе — обычный режим
выделения (`README.md:52`). Ошибка — сброс прямоугольника и обычный режим.

### 1.18 Автозапуск и single instance

**Автозапуск.** Windows: значение `SnapBrief` в разделе реестра
`HKCU\Software\Microsoft\Windows\CurrentVersion\Run`, содержащее **полный путь к EXE в кавычках**
(`WindowsStartupService.cs:9-27`). Включено тогда и только тогда, когда значение точно равно команде
**этого** экземпляра (сравнение без учёта регистра). Выключение удаляет значение **только если оно
совпадает** с нашей командой — чужие записи не трогаются. По умолчанию выключено
(`tasks/verification.md:101`). macOS-эквивалент — §9.4.

**Single instance.** Windows (`App.xaml.cs:25-32`, `SingleInstanceActivation.cs`):
1. Именованный мьютекс `Local\SnapBrief.Desktop.SingleInstance`.
2. Если мьютекс уже занят — второй экземпляр **не создаёт окно**, отправляет первому команду
   «показать» и завершается с кодом 0.
3. Канал: named pipe `SnapBrief.Desktop.Activation.v1.{SessionId}` (сессия текущего пользователя)
   с флагом «только текущий пользователь» (`SingleInstanceActivation.cs:16`, `:142`).
4. Протокол: ровно **5 байт ASCII `SHOW` плюс перевод строки**, ответ — один байт `0x06` (ACK).
   Любое другое сообщение отклоняется (`IsShowCommand`, `:84`): без перевода строки, с CRLF,
   с хвостом после перевода строки, `OPEN` — всё невалидно.
5. Таймауты: попытка подключения не более **250 мс**, общий бюджет **2 секунды**, пауза между
   попытками не более 60 мс (`App.xaml.cs:28`, `SingleInstanceActivation.cs:51`, `:78`);
   обмен на стороне сервера — не более **1 секунды** (`:103`).
6. Приняв команду, первый экземпляр показывает стопку без активации, разворачивает окно
   из минимизированного состояния и активирует его (`App.xaml.cs:77-85`).
7. При `--smoke-test` мьютекс **не** берётся (`App.xaml.cs:24`) — smoke может идти параллельно
   с рабочим экземпляром.

macOS-эквивалент — §9.6.

### 2.5 SessionValidation (`Core/Models/SessionValidation.cs:5-80`)

Валидация вызывается при **каждом** сохранении, загрузке, любой операции над сессией и перед
экспортом. Проверки по порядку и **точные тексты ошибок**:

1. Сессия не null.
2. `Id` не пустой GUID — иначе `Session ID cannot be empty.`
3. `SchemaVersion == 1` — иначе `Unsupported session schema version: {N}.`
4. `Revision >= 0` — иначе `Session revision cannot be negative.`
5. Для каждого снимка:
   - `Id` не пустой и **уникален в сессии** — иначе `Capture IDs must be non-empty and unique.`
   - `SourceImagePath` **не абсолютный** и не содержит компонента `..` — иначе
     `Capture image paths must be relative and cannot escape the session directory.`
   - `PixelWidth > 0`, `PixelHeight > 0`, `DpiX > 0`, `DpiY > 0` — иначе
     `Capture dimensions and DPI must be positive.`
6. Для каждой отметки:
   - `Id` не пустой и **уникален во всей сессии** (не только внутри снимка) — иначе
     `Annotation IDs must be non-empty and unique within a session.`
   - `Thickness > 0` и `Points` непуст — иначе
     `Annotations require positive thickness and geometry.`
   - все точки конечны и лежат в `[0,1]` по обеим осям — иначе
     `Annotation coordinates must be normalized to the [0, 1] image space.`
   - если `PathSegments` непуст: вид должен быть **Freehand или Highlight**, и каждый сегмент
     должен содержать **минимум 2 точки** — иначе `Only freehand and highlight annotations may
     contain multi-segment paths, and every segment requires at least two points.`
   - все точки всех сегментов конечны и в `[0,1]` — иначе
     `Annotation path-segment coordinates must be normalized to the [0, 1] image space.`

На Swift: бросать типизированную ошибку `SessionValidationError` с теми же сообщениями; тесты
проверяют факт отказа, а не текст, но сообщения полезны для журнала.

### 2.6 SessionOperations и SessionHistory

**SessionOperations** (`Core/Editing/SessionOperations.cs:6-68`) — чистые функции над сессией.
Каждая изменяющая операция завершается общим шагом Touch: `ModifiedAtUtc = nowUtc`,
`Revision = Revision + 1` **с проверкой переполнения**, затем полная валидация (`:49-54`).

| Операция | Поведение |
|---|---|
| `AddCapture(session, capture, now)` | добавить в конец, Touch |
| `RemoveCapture(session, captureId, now)` | найти индекс, удалить, Touch. Отсутствие снимка — ошибка `Capture {id} does not exist in this session.` |
| `MoveCapture(session, captureId, destIndex, now)` | `destIndex` вне `[0, count)` — ошибка диапазона. Если индекс не изменился — вернуть **ту же** сессию без Touch. Иначе удалить и вставить, Touch |
| `UpdateGlobalNote(session, note, now)` | если текст совпадает — вернуть ту же сессию; иначе заменить, Touch |
| `UpdateCapture(session, capture, now)` | заменить снимок по его Id; если новое значение равно старому — вернуть ту же сессию; иначе заменить, Touch |

**SessionHistory** (`Core/Editing/SessionHistory.cs:5-67`) — undo/redo на уровне сессии.
Используется тестами; в текущем UI оверлей ведёт собственную историю (§1.5), но алгоритм
воспроизвести обязательно — он покрыт тестами.

- Конструктор: начальная сессия, необязательный источник времени.
- `Current` — текущая сессия; `CanUndo` и `CanRedo` — непустота стеков.
- `Apply(operation)` (`:21-33`): вычислить `next = operation(Current)`. Если `next` — **тот же объект
  или равен по значению** текущему, ничего не делать. Иначе: положить `Current` в стек undo,
  **очистить redo**, установить `Current = next`.
- `Undo()` (`:35-46`): если undo пуст — вернуть false. Снять верх undo, положить **текущее** состояние
  в redo, восстановить снятое **как новую ревизию**, вернуть true.
- `Redo()` (`:48-59`): симметрично.
- **Ключевая деталь** `RestoreAsNewRevision` (`:61-66`): восстановленное состояние получает
  `Revision = current.Revision + 1` (с проверкой переполнения) и `ModifiedAtUtc = now`.
  То есть undo **не откатывает** номер ревизии, а увеличивает его. Это проверено тестом
  `Reorder_remove_and_undo_preserve_capture_identity_and_labels_follow_order`, где после
  add, add, move, remove, undo итоговая ревизия равна **5**.

### 2.7 CaptureCropper (`Core/Editing/CaptureCropper.cs:19-250`)

Обрезает снимок и **пересчитывает координаты отметок**, сохраняя их идентификаторы и заметки.

Вход: снимок, `NormalizedRect(X, Y, Width, Height)` в нормализованных координатах текущего
изображения, новый относительный путь, новые пиксельные размеры.
Выход: `CropResult(PreviousCapture, CroppedCapture, RemovedAnnotationIds)` (`:14-17`).

`NormalizedRect` (`:6-12`) даёт производные `Left = X`, `Top = Y`, `Right = X + Width`,
`Bottom = Y + Height`. Константа `Epsilon = 1e-12` (`:21`).

#### Валидация входа (`ValidateCrop`, `:232-249`)

- Все четыре компонента прямоугольника конечны; `X >= 0`, `Y >= 0`, `Width > 0`, `Height > 0`,
  `Right <= 1`, `Bottom <= 1` — иначе ошибка диапазона с сообщением
  `Crop bounds must be a positive rectangle within normalized [0, 1] image space.`
- Путь непуст и не состоит из пробелов.
- Путь **не абсолютный** и без компонента `..` — иначе
  `Cropped source image path must remain relative to the session directory.`
- `pixelWidth > 0`, `pixelHeight > 0`.

#### Обработка отметок (`:33-71`)

Для каждой отметки, в исходном порядке:

- **Freehand и Highlight** — обрезка полилинии. Если ни одного видимого отрезка не осталось,
  идентификатор попадает в список удалённых. Иначе `Points` = первый сегмент, а `PathSegments`
  заполняется **только если сегментов больше одного** (иначе пустой массив, что корректно
  с точки зрения валидации).
- **Arrow** — обрезка отрезка.
- **Rectangle, Text, Redaction, Blur** — обрезка прямоугольника.
- Прочее — пустой результат, то есть удаление.

Итог: новый снимок — копия исходного с новым путём, новыми размерами и отфильтрованным списком
отметок. **`Id`, `Title`, `Note`, `DpiX`, `DpiY` сохраняются** (`:73-79`).
Исходный снимок **не мутируется** — он возвращается как `PreviousCapture`.

#### CropLine (`:83-94`)

Если точек меньше двух, или отрезок не пересекает прямоугольник, или длина после клиппинга не больше
`Epsilon` — пустой результат. Иначе обе клиппированные точки переводятся в систему обрезки.

#### CropBox (`:96-115`)

```
left   = max(min(p0.x, p1.x), crop.Left)
top    = max(min(p0.y, p1.y), crop.Top)
right  = min(max(p0.x, p1.x), crop.Right)
bottom = min(max(p0.y, p1.y), crop.Bottom)
если right - left <= Epsilon или bottom - top <= Epsilon: пусто
результат: [map(left, top), map(right, bottom)]
```

Результат всегда нормализуется в порядок «левый-верхний, правый-нижний», независимо от того,
в каком направлении пользователь рисовал прямоугольник.

#### CropPolyline (`:117-152`)

Идёт по всем сегментам, внутри каждого — по парам соседних точек:
- если пара не пересекает прямоугольник или её длина не больше `Epsilon`, текущий пробег
  завершается (пробег из 2 и более точек сохраняется);
- если текущего пробега нет **или** новая начальная точка отстоит от последней точки пробега
  больше чем на `Epsilon`, предыдущий пробег завершается и начинается новый;
- конечная точка добавляется, только если она отличается от последней больше чем на `Epsilon`.

Затем оставляются только пробеги из 2 и более точек с суммарной длиной больше `Epsilon`, и все точки
переводятся в систему обрезки. **Разорванные части линии не склеиваются** — отдельное требование
(`tasks/verification.md:30`) и отдельный тест.

#### Клиппинг отрезка (`TryClipSegment`, `:163-188`)

Алгоритм Лианга–Барски с параметром `t` в `[0,1]`:

```
dx = end.x - start.x ; dy = end.y - start.y
t0 = 0 ; t1 = 1
ClipTest(-dx, start.x - crop.Left,   t0, t1)
ClipTest( dx, crop.Right - start.x,  t0, t1)
ClipTest(-dy, start.y - crop.Top,    t0, t1)
ClipTest( dy, crop.Bottom - start.y, t0, t1)
clippedStart = start + t0 * (dx, dy)
clippedEnd   = start + t1 * (dx, dy)
```

`ClipTest(denominator, numerator, t0, t1)` (`:190-209`):
- если `abs(denominator) <= Epsilon` — вернуть `numerator >= 0` (отрезок параллелен границе);
- `r = numerator / denominator`;
- если `denominator < 0`: `r > t1` — отказ; `r > t0` — присвоить `t0 = r`;
- иначе: `r < t0` — отказ; `r < t1` — присвоить `t1 = r`.

#### Перевод в систему обрезки (`MapToCrop`, `:211-213`)

```
x = clamp((point.x - crop.Left) / crop.Width,  0, 1)
y = clamp((point.y - crop.Top)  / crop.Height, 0, 1)
```

### 2.8 RegionBlur (`App/Imaging/RegionBlur.cs:9-138`)

Размывает **один прямоугольник** в пиксельных координатах исходника, не трогая остальное изображение.

Константы: 4 байта на пиксель, **3 прохода** (`PassCount = 3`), максимальный радиус **512**.

Алгоритм `Apply(source, pixelRegion, radius)` (`:15-45`):
1. Радиус вне диапазона 1..512 — ошибка диапазона с сообщением
   `Blur radius must be between 1 and 512 pixels.`
2. Изображение приводится к формату BGRA-8888 (если оно уже в нём — используется как есть).
3. Копируются **все** пиксели в буфер, stride = `width * 4`.
4. Прямоугольник клиппируется по границам изображения (`Clip`, `:47-58`): нулевые или отрицательные
   размеры и пустое пересечение дают пустой прямоугольник, и тогда изображение копируется
   **без изменений**.
5. Если пересечение непусто — размывается только область.
6. Результат создаётся заново с **исходными DpiX и DpiY** и замораживается.
   Исходное изображение **не мутируется**.

Размытие области (`BlurRegion`, `:60-83`):
1. Пиксели области копируются в отдельный буфер со своим stride `region.Width * 4`, плюс
   вспомогательный буфер того же размера.
2. **Три прохода**, каждый: горизонтальный box-blur из основного буфера во вспомогательный,
   затем вертикальный box-blur из вспомогательного обратно в основной.
3. Результат копируется обратно в полный буфер построчно.

Box-blur (`:85-125`): скользящее окно шириной `2 * radius + 1`, суммы по всем 4 каналам,
координаты **зажимаются** к краям области (`clamp(x, 0, width - 1)`), то есть краевые пиксели
дублируются. Запись значения (`WriteAverage`, `:133-137`):
`pixel = (sum + divisor / 2) / divisor` — округление к ближайшему.

Три прохода box-blur аппроксимируют гауссово размытие. **Это не эквивалентно CIGaussianBlur.**
На macOS реализовать тот же трёхпроходный box-blur (например, `vImageBoxConvolve_ARGB8888`
из Accelerate трижды, с `kvImageEdgeExtend`), иначе результат не совпадёт с Windows-версией
пиксель в пиксель и не пройдут переносимые тесты §8.1.

Радиус, применяемый интерфейсом: `clamp(round(thickness * 3), 4, 36)` (`AnnotationCanvas.cs:463`,
`WpfExportImageRenderer.cs:77`).

### 2.9 ResizeGeometry (`App/Controls/ResizeGeometry.cs:6-37`)

Общая математика для ручек изменения размера — и у отметок, и у границ снимка.

- `Corners(bounds)` — четыре угла **по часовой стрелке**: TopLeft, TopRight, BottomRight, BottomLeft.
- `HitCorner(bounds, point, radius)` — индекс первого угла, до которого расстояние не больше `radius`,
  иначе `-1`. Порядок проверки — по часовой стрелке с индекса 0.
- `Resize(original, corner, point, limit, minimum)` (`:19-32`):

  ```
  minX = min(minimum, original.Width)
  minY = min(minimum, original.Height)
  left, top, right, bottom = original.Left, original.Top, original.Right, original.Bottom
  если corner = 0 или 3:  left   = clamp(point.x, limit.Left,  right - minX)
  иначе:                  right  = clamp(point.x, left + minX, limit.Right)
  если corner = 0 или 1:  top    = clamp(point.y, limit.Top,   bottom - minY)
  иначе:                  bottom = clamp(point.y, top + minY,  limit.Bottom)
  результат = прямоугольник (left, top) .. (right, bottom)
  ```

  Свойства: противоположный угол остаётся неподвижным; инверсия невозможна; результат не выходит
  за `limit`. Если исходный прямоугольник уже меньше `minimum`, минимум ужимается до его размера.
- `Map(point, original, resized)` (`:34-36`) — пропорциональный перенос точки:

  ```
  x = resized.Left + (point.x - original.Left) * resized.Width  / max(1, original.Width)
  y = resized.Top  + (point.y - original.Top)  * resized.Height / max(1, original.Height)
  ```

  Делитель защищён от нуля через `max(1, ...)`.

### 2.10 Инварианты, обязательные к сохранению в порте

1. Идентификаторы снимков и отметок **никогда не меняются** при переупорядочивании, undo,
   обрезке и изменении границ (`tasks/prd-snapbrief.md:259`).
2. Отображаемые метки — производная от **позиции** в списке, а не хранимое поле (§4.1).
3. Координаты отметок хранятся **только нормализованными** к текущему изображению снимка.
   Три пространства координат — экранные пиксели, DIP окна и пиксели изображения — не смешиваются
   (`tasks/prd-snapbrief.md:257`). Преобразования: экран в DIP через масштаб окна оверлея,
   DIP в пиксели изображения через прямоугольник отображения холста, пиксели в нормализованные
   через размер изображения.
4. Удаление отметки удаляет её заметку **одной отменяемой операцией** (`tasks/prd-snapbrief.md:259`).
5. Любое изменение разметки, blur или обрезки делает ранее подготовленный пакет устаревшим и
   требует нового экспорта до вставки (`tasks/prd-snapbrief.md:168`). В коде это инвалидация
   подготовленного экспорта (`EdgeStackWindow.xaml.cs:603`).
6. Исходные пиксели сохраняются **до** декорирования; обрезка создаёт новую версию пикселей
   без перезаписи исходника (`tasks/prd-snapbrief.md:168`).

## 3. Персистентность

### 3.1 Параметры сериализации (`Infrastructure/Serialization/SnapBriefJson.cs:6-14`)

Единые настройки для `session.json` **и** `manifest.json`:

- **camelCase** для всех имён свойств;
- **отступы включены** (pretty-print, 2 пробела);
- перечисления пишутся **строками в camelCase**: `arrow`, `rectangle`, `highlight`, `freehand`,
  `text`, `redaction`, `blur`;
- даты — момент времени с оффсетом, формат ISO-8601 **с оффсетом и до 7 знаков долей секунды**,
  например `2026-09-08T23:01:04.7472364+00:00`;
- GUID — строка в каноническом виде с дефисами и в нижнем регистре, например
  `5dd95f4e-c52d-4bba-b532-160760391098`;
- не-ASCII символы **экранируются как \uXXXX** (поведение сериализатора по умолчанию);
  на macOS допустимо писать UTF-8 напрямую, поскольку JSON-парсеры равнозначно читают оба варианта.
  **Схема при этом совместима, байты — нет.** Если нужна побайтная идентичность, экранировать так же.

Отдельно: `settings.json` и `last-region.json` используют **другой** сериализатор — со свойствами
в **PascalCase** и без конвертера перечислений
(`HotkeySettingsWindow.xaml.cs:54`, `OverlayEditorWindow.Save.cs:55`).

### 3.2 Формат session.json

Реальный файл, снятый с рабочей сборки
(`.tmp/note-smoke-370ffa2874b14e6e87b67a49f56307f5/5dd95f4ec52d4bbab532160760391098/session.json`,
не-ASCII развёрнут для читаемости):

```json
{
  "id": "5dd95f4e-c52d-4bba-b532-160760391098",
  "schemaVersion": 1,
  "createdAtUtc": "2026-09-08T23:01:04.0462779+00:00",
  "modifiedAtUtc": "2026-09-08T23:01:04.3890324+00:00",
  "revision": 1,
  "globalNote": "Сохранить цвета",
  "selectedTargetProfileId": "codex-desktop",
  "captures": [
    {
      "id": "262a4b2e-3f69-47bb-8181-3d29d4ddf7c4",
      "sourceImagePath": "source\262a4b2e3f6947bb81813d29d4ddf7c4.png",
      "pixelWidth": 1920,
      "pixelHeight": 1080,
      "dpiX": 144,
      "dpiY": 144,
      "title": "",
      "note": "",
      "annotations": [
        {
          "id": "eea10c8c-09e5-469a-b919-9e5f7f3c540a",
          "kind": "arrow",
          "points": [
            { "x": 0.546875, "y": 0.6018518518518519 },
            { "x": 0.7916666666666666, "y": 0.8148148148148148 }
          ],
          "strokeColor": "#FF315CF5",
          "thickness": 6,
          "text": "Текст",
          "note": "Увеличить кнопку",
          "pathSegments": []
        }
      ]
    }
  ]
}
```

Обязательные наблюдения:

1. Порядок ключей сессии: `id`, `schemaVersion`, `createdAtUtc`, `modifiedAtUtc`, `revision`,
   `globalNote`, `selectedTargetProfileId`, `captures`.
2. Порядок ключей снимка: `id`, `sourceImagePath`, `pixelWidth`, `pixelHeight`, `dpiX`, `dpiY`,
   `title`, `note`, `annotations`.
3. Порядок ключей отметки: `id`, `kind`, `points`, `strokeColor`, `thickness`, `text`, `note`,
   `pathSegments`. Поле `pathSegments` идёт **последним**, потому что это отдельное init-свойство,
   а не параметр конструктора.
4. `pathSegments` **всегда присутствует**; пустой массив, когда сегментов нет.
5. `selectedTargetProfileId` пишется как `null`, если профиль не выбран.
6. **`sourceImagePath` записывается с разделителем текущей ОС**; на Windows это обратный слэш,
   в JSON экранированный как двойной. Критично для порта, см. §3.7.
7. `strokeColor` — восемь hex-цифр **заглавными** с ведущим `#`, порядок `AARRGGBB`.
8. `thickness` — число; целые значения пишутся без дробной части.
9. `pixelWidth` и `pixelHeight` целые; `dpiX` и `dpiY` числа, целые пишутся без дробной части.

### 3.3 Структура каталога данных

Windows, режим по умолчанию:

```
%LOCALAPPDATA%\SnapBrief\
  settings.json                     <- настройки, PascalCase JSON
  last-region.json                  <- последняя область, PascalCase JSON, только если включено
  sessions\
    startup.log                     <- журнал старта
    current-session.txt             <- GUID текущей сессии, формат D, с дефисами
    <session-id-N>\                 <- GUID сессии, формат N, 32 hex без дефисов
      session.json
      .session-<guid-N>.tmp         <- временный файл при записи, удаляется
      source\
        <capture-id-N>.png          <- исходники снимков и производные обрезки
      exports\
        .staging-<export-id-N>\     <- временный каталог экспорта, переименовывается
        revision-000001-<export-id-N>\
          A_<capture-id-N>.png
          B_<capture-id-N>.png
          prompt.md
          manifest.json
```

Ключевые детали путей:
- корень сессий — `%LOCALAPPDATA%\SnapBrief\sessions` (`JsonSessionStore.cs:22-26`);
- **каталог настроек на уровень выше**: `%LOCALAPPDATA%\SnapBrief\settings.json`
  (`EdgeStackWindow.xaml.cs:60`, `SessionWorkspace.cs:34`);
- имя каталога сессии — GUID в формате N, то есть **32 hex-символа без дефисов**
  (`JsonSessionStore.cs:28`);
- указатель `current-session.txt` содержит GUID в формате D, то есть **с дефисами**
  (`SessionWorkspace.cs:145`) и лежит **внутри** каталога `sessions`
  (`SessionWorkspace.cs:33`, `tasks/verification.md:57`).

Режим `--data-dir X` (`EdgeStackWindow.xaml.cs:57-60`, `SessionWorkspace.cs:28-34`):

```
X\
  settings.json
  last-region.json
  startup.log
  current-session.txt
  <session-id-N>\ ...
```

То есть при явном каталоге данных сессии лежат **прямо в X**, а не в подпапке `sessions`,
и настройки тоже в X. Отдельная ветка, воспроизвести точно.

Режим `--demo` без `--data-dir`: корень `{TEMP}\SnapBrief\demo-{PID}`.

### 3.4 Запись сессии (`Infrastructure/Persistence/JsonSessionStore.cs`)

Сохранение (`:30-77`):
1. Полная валидация сессии (§2.5) — до любых обращений к диску.
2. Взять **монотонный номер сохранения** (атомарный инкремент счётчика процесса).
3. Захватить семафор — одна запись за раз.
4. **Отбросить устаревшую запись**: если для этой сессии уже зафиксирован номер не меньше нашего —
   выйти, ничего не записав (`:38-41`). Это гарантирует, что при наложении сохранений на диск
   попадёт **последний вызванный**, даже если ревизии совпадают
   (тест `Overlapping_saves_commit_the_latest_invocation_even_when_revisions_repeat`).
5. Создать каталог сессии.
6. Записать во временный файл `.session-{новый-guid-N}.tmp` в **том же каталоге**,
   режим «создать новый», без разделения доступа, буфер 65536, асинхронно и со сквозной записью.
7. Сбросить буферы.
8. **Атомарно переместить** временный файл на `session.json` с перезаписью.
9. Зафиксировать номер сохранения.
10. В блоке finally удалить временный файл, если он остался.

Загрузка (`:79-92`):
- если `session.json` не существует — вернуть пусто;
- прочитать и разобрать; если результат пуст — ошибка `Session JSON did not contain a session.`;
- **выполнить полную валидацию** и только потом вернуть.

**macOS:** атомарная замена — `FileManager.replaceItemAt` или `Data.write(to:options: .atomic)`.
Семафор — `NSLock` либо actor; монотонный счётчик достаточно держать внутри того же actor.

### 3.5 Запись исходников (`Infrastructure/Persistence/SessionAssetStore.cs`)

Сохранение исходного PNG (`:9-45`):
1. Поток должен быть читаемым, иначе ошибка `PNG content stream must be readable.`
2. Относительный путь результата: `source/{captureId-N}.png`, где N — 32 hex без дефисов.
3. Создать каталог `source` внутри каталога сессии.
4. Записать во временный файл `.{captureId-N}-{новый-guid-N}.tmp` в том же каталоге `source`.
5. **Проверить сигнатуру PNG** первых 8 байт: `137 80 78 71 13 10 26 10`, иначе ошибка
   `Capture content is not a PNG image.`
6. Атомарно переместить на целевой путь с перезаписью.
7. В блоке finally удалить временный файл, если остался.

Сохранение производного изображения (`SessionWorkspace.cs:79-85`) использует тот же механизм,
но с **новым случайным GUID** вместо идентификатора снимка — так производные обрезки не затирают
исходник.

Кодирование PNG выполняется **в фоновом потоке** с уже замороженным изображением
(`SessionWorkspace.cs:87-101`) — осознанная оптимизация (`tasks/verification.md:67`).

### 3.6 Жизненный цикл рабочей области (`SessionWorkspace`)

- При создании: новый GUID сессии, дата создания = сейчас, ревизия 0 (`:35-36`).
- Загрузка текущей (`:47-67`): прочитать `current-session.txt`; если файла нет или содержимое
  не разбирается как GUID — вернуть пустой список. Загрузить сессию; если её нет — пустой список.
  Иначе принять её идентификатор, ревизию, дату создания, legacy-заметку и профиль.
  Для каждого снимка собрать полный путь; **если файл отсутствует, снимок молча пропускается**
  (`:63`). Это защита от потери всей сессии из-за одного удалённого файла.
- Снимок состояния (`:133-139`): новая сессия с **предынкрементом ревизии**,
  датой изменения = сейчас и текущим списком снимков.
- Сохранение снимка состояния (`:141-146`): сохранить сессию, создать корень,
  **перезаписать `current-session.txt`** идентификатором сохранённой сессии.
- Старт новой сессии (`:108-124`): сохранить текущую, создать новую пустую, сохранить её
  (указатель переезжает), затем переключить внутреннее состояние на новую сессию и сбросить
  legacy-заметку и профиль.
- Подготовка экспорта (`:126-131`): создать снимок состояния, сохранить его, затем выполнить
  экспорт (§4). То есть **каждая подготовка пакета увеличивает ревизию и пишет `session.json`**.
- Автосохранение с debounce **500 мс** (`EdgeStackWindow.xaml.cs:67`, `:604-605`); по срабатыванию
  таймера — сохранение и обновление буфера. При закрытии окна — принудительное сохранение,
  и если оно не удалось, окно **не** закрывается (`:764-772`).

стандартное место для такого состояния. Пользовательские экспорты («Сохранить пакет…», Cmd+S) идут
туда, куда указал пользователь; папка быстрого сохранения по умолчанию — `~/Pictures/SnapBrief`
(соответствие Windows-дефолту `{Изображения}/SnapBrief`).

**Требование совместимости схемы.** JSON, записанный macOS-версией, должен читаться
Windows-версией и наоборот. Обязательные правила:

1. Имена ключей, их порядок, camelCase, отступы, строковые camelCase-перечисления — как в §3.1.
2. **Разделитель в `sourceImagePath` записывать как прямой слэш**, то есть `source/xxx.png`.
   Обоснование: значение всегда собирается из фиксированного префикса `source` и имени файла;
   валидация (§2.5) разбивает путь по **обоим** разделителям, а Windows одинаково принимает
   и прямой, и обратный слэш при открытии файла — то есть macOS-файл прочитается на Windows.
   Обратная совместимость: **macOS-версия обязана при чтении заменять обратный слэш на прямой**,
   иначе старые Windows-сессии не откроются. Это единственное расхождение по байтам,
   и оно односторонне безопасно.
3. Формат даты: сохранять оффсет и до 7 знаков долей секунды, шаблон
   `yyyy-MM-dd'T'HH:mm:ss.SSSSSSSXXXXX`. На Swift это не даёт `ISO8601DateFormatter` из коробки:
   нужен `DateFormatter` с локалью `en_US_POSIX` либо ручная сборка строки из компонентов.
   При чтении принимать 0..7 знаков долей и любой оффсет.
4. GUID в нижнем регистре с дефисами в JSON; в **именах файлов и каталогов** — 32 hex-символа
   **без** дефисов, нижний регистр.
5. `strokeColor` — заглавные hex, формат `#AARRGGBB`.
6. Числа: не сериализовать целые как `1.0`, писать `1`.

### 3.8 Требования к отказоустойчивости

- Ошибка буфера, диска или фокуса **не уничтожает сессию**; повторный запуск восстанавливает
  последний успешно сохранённый вариант (`tasks/prd-snapbrief.md:288`).
- Экспорты **не удаляются** при копировании, вставке или выходе — агент может открыть файлы позже;
  автоматическая очистка выключена (`tasks/prd-snapbrief.md:273`).
- Завершённые сессии сохраняются отдельно, их снимки и заметки **не подмешиваются** в новые
  (`tasks/prd-snapbrief.md:442`).
- При отсутствии файла исходника снимок пропускается, остальная сессия загружается (§3.6).

## 4. Экспорт

### 4.1 Метки (`Core/Exporting/CaptureLabels.cs:7-36`)

- Метка снимка по индексу: `A` для 0, `B` для 1 и так далее — просто символ `A` плюс индекс.
  Индекс вне диапазона 0..25 — ошибка диапазона. То есть **максимум 26 снимков в одном пакете**.
- Метка отметки: конкатенация метки снимка и **однобазового номера**: `A1`, `A2`, `B1`.
- Перечисление помеченных отметок (`:22-35`) выдаёт **только отметки с непустой заметкой**,
  в порядке их следования в списке, присваивая последовательные номера начиная с 1.
  Отметки без заметки **пропускаются и не занимают номер**.

«Непустая заметка» определяется как `ExportText.HasContent` (`Core/Exporting/ExportText.cs:5`):
строка существует, не пустая и **не состоит только из пробельных символов** (пробел, табуляция,
CR, LF).

### 4.2 Генератор текста (`Core/Exporting/PromptGenerator.cs:8-46`)

Алгоритм:
1. Полная валидация сессии.
2. Собрать список секций.
3. Если `GlobalNote` имеет содержимое — первой секцией добавить
   `Общее пожелание:` плюс перевод строки плюс текст.
   В текущем UI это поле всегда пустое (§1.4), но алгоритм сохраняем.
4. Для каждого снимка по порядку:
   - начать с `Снимок {метка}`;
   - если `Title` имеет содержимое — дописать пробел, длинное тире, пробел и `Title`.
     **UI никогда не заполняет Title**, поэтому в реальных пакетах этого не бывает;
   - дописать точку;
   - если `Note` снимка имеет содержимое — дописать перевод строки, `Комментарий к снимку:`,
     перевод строки и текст;
   - для каждой отметки с непустой заметкой — дописать перевод строки, метку, двоеточие с пробелом
     и текст заметки.
5. Секции склеить через **два перевода строки**.

**Текст пользователя переносится дословно**, без пересказа, обрезки и нормализации пробелов
(FR-07, `tasks/prd-snapbrief.md:149`). Ведущие и хвостовые пробелы внутри заметки сохраняются:
тест `Whitespace_only_notes_are_not_labeled_exported_or_counted_but_real_text_is_preserved`
ожидает в тексте подстроку с тремя пробелами после двоеточия и двумя перед переводом строки.

#### Пример реального вывода

Файл `prompt.md` из рабочей сборки
(`.tmp/note-smoke-370ffa2874b14e6e87b67a49f56307f5/.../prompt.md`):

```text

Сохранить цвета

Снимок A.
A1: Увеличить кнопку

Снимок B.
B1: Перенести пункт выше

Текст обрезается

### 4.3 Контракты экспорта (`Core/Exporting/ExportContracts.cs`)

`ExportImageEntry` (`:6-11`): `CaptureId`, `DisplayLabel`, `FileName`, `Sha256`, `ByteLength`.

`ExportManifest` (`:13-23`), порядок полей равен порядку ключей в JSON:

### 4.4 FileExportService (`Infrastructure/Exporting/FileExportService.cs:16-96`)

1. Полная валидация сессии.
2. Пустая сессия — ошибка `Cannot export a session without captures.`
3. Каталог сессии обязателен и приводится к абсолютному пути.
4. Новый идентификатор экспорта (GUID).
5. Каталоги: `exports`, временный `exports/.staging-{exportId-N}`,
   финальный `exports/revision-{ревизия шестизначная с ведущими нулями}-{exportId-N}`.
6. Для каждого снимка по порядку:
   - метка по индексу;
   - имя файла `{метка}_{captureId-N}.png`, пример `A_262a4b2e3f6947bb81813d29d4ddf7c4.png`;
   - разрешить путь исходника **строго внутри каталога сессии** (`:104-114`); выход за пределы —
     ошибка `Capture image path escapes the session directory.`;
   - отсутствие исходника — ошибка «файл не найден»;
   - вызвать рендерер, записав результат в файл в staging;
   - **проверить сигнатуру PNG** результата, иначе ошибка
     `The export renderer did not produce a PNG image.`;
   - записать размер файла и SHA-256 в **нижнем регистре hex**, 64 символа.
7. Сгенерировать текст задания, записать `prompt.md` в **UTF-8 без BOM**.
8. Собрать manifest, посчитать `NoteCount` (`:98-102`): единица, если `globalNote` непуст, плюс
   по каждому снимку единица, если его заметка непуста, плюс число отметок с непустой заметкой.
9. Записать `manifest.json` теми же настройками сериализации (§3.1).
10. **Атомарно переименовать** staging-каталог в финальный. Только после этого экспорт считается
    опубликованным.
11. При любой ошибке staging-каталог удаляется рекурсивно, исключение пробрасывается —
    **частичная ревизия не публикуется**.

Экспорт **не содержит исходников** — только отрендеренные PNG, `prompt.md` и `manifest.json`
(`tasks/prd-snapbrief.md:275`).

### 4.5 Рендер экспортного PNG (`App/WpfExportImageRenderer.cs:17-150`)

Итоговое изображение: **ширина равна ширине исходника**, **высота равна высоте исходника плюс 48**
(константа `HeaderHeight = 48`, `:19`). DPI результата — **96 на 96**, формат — premultiplied BGRA.

Порядок отрисовки (`:26-41`):

1. Белый прямоугольник шапки: от (0,0) размером `width x 48`.
2. Изображение снимка **со всеми применёнными blur-областями**, в прямоугольник
   `(0, 48, width, height)`.
3. Бейдж снимка (`DrawCaptureBadge`, `:60-66`):
   - скруглённый прямоугольник, координаты `(12, 8)`, размер `34 x 32`, радиусы 7 и 7,
     заливка `#172033` без обводки;
   - текст метки: точка `(23, 13)`, размер 16, начертание Bold, белый;
   - подпись `SNAPBRIEF · СНИМОК`: точка `(57, 16)`, размер 12, начертание SemiBold, цвет `#5E687A`.
   - Шрифт всех надписей шапки — **Segoe UI**; на macOS использовать системный шрифт SF Pro
     с теми же кеглями и начертаниями.
4. Отметки **всех видов, кроме Blur и Redaction** — только формы, без подписей.
5. Отметки вида **Redaction** — только формы (чтобы сплошное скрытие легло **поверх** остальных
   правок, `tasks/verification.md:29`).
6. **Все** отметки — только круглые подписи-номера, без форм.

Применение blur перед отрисовкой (`ApplyBlurAnnotations`, `:68-80`): для каждой blur-отметки
с двумя и более точками прямоугольник в пикселях исходника вычисляется как

```
left   = clamp(floor(min(p0.x, p1.x) * width),   0,    width)
top    = clamp(floor(min(p0.y, p1.y) * height),  0,    height)
right  = clamp(ceil (max(p0.x, p1.x) * width),   left, width)
bottom = clamp(ceil (max(p0.y, p1.y) * height),  top,  height)
радиус = clamp(round(thickness * 3), 4, 36)
```

Размытия применяются **последовательно**, каждое к результату предыдущего.

#### Отрисовка формы (`DrawAnnotation`, `:82-142`)

Отображение нормализованной точки: `x = p.x * width`, `y = p.y * height + 48`.
Цвет берётся из строки `#AARRGGBB`. Толщина пера — **`item.Thickness` в пикселях изображения
без масштабирования**; концы и стыки скруглённые.

| Вид | Отрисовка |
|---|---|
| Freehand | линии по всем сегментам, перо цвета отметки, толщина `Thickness` |
| Highlight | то же, но цвет с **альфой 90** из 255 и толщина `Thickness * 4` |
| Rectangle | контур прямоугольника от точки 0 до точки 1, без заливки |
| Redaction | **сплошная чёрная заливка** прямоугольника, без обводки |
| Text | текст `item.Text`, кегль `max(16, Thickness * 4.5)`, начертание SemiBold, цвет отметки, в точке 0 |
| Arrow | линия от точки 0 к точке 1 плюс закрашенный треугольник у точки 1 |

Геометрия наконечника стрелки (`:110-128`):

```
direction = normalize(start - end)
side      = (-direction.y, direction.x)
size      = max(12, Thickness * 3.2)
треугольник: end,
             end + direction * size + side * size * 0.45,
             end + direction * size - side * size * 0.45
заливка цветом отметки, без обводки
```

Blur и Crop форму не рисуют (для Blur пиксели уже размыты, Crop до экспорта не доживает).

#### Круглая подпись-номер (`:132-141`)

Рисуется **только** если у отметки есть отображаемая метка, то есть только для отметок с непустой
заметкой.

```
anchor   = точка 0 отметки в координатах результата
diameter = max(34, длина_метки * 9 + 16)
center   = (anchor.x, max(diameter / 2 + 2, anchor.y - diameter / 2 - 4))
```

- Круг: заливка `#2F8CFF`, без обводки, радиус `diameter / 2`.
- Текст метки: кегль **13**, начертание Bold, белый, шрифт Segoe UI, отцентрован по кругу
  (`center - (width/2, height/2)` текста).
- Ограничение `max(diameter/2 + 2, ...)` не даёт кругу уехать выше верхней границы изображения.

### 4.6 Экранный рендер с разметкой (`AnnotationCanvas.RenderAnnotated`, `:270-289`)

Используется для **сохранения в файл (Ctrl+S)** — там нет шапки и подписей-меток в том же виде,
что в экспорте.

- Результат: изображение **точно размера исходника**, DPI 96 на 96, premultiplied BGRA.
- Отрисовка: сначала изображение со всеми blur, затем формы всех отметок кроме Blur и Redaction,
  затем формы Redaction, затем **подписи-номера всех отметок** (`:280-282`).
- Метка берётся из свойства `Label` отметки, которое пересчитывается при каждом изменении заметок
  (`OverlayEditorWindow.RefreshLabels`, `:436-450`) по тому же правилу §4.1.
- Круг подписи на холсте (`AnnotationCanvas.cs:393-402`): `diameter = max(26, длина_метки * 7 + 12)`,
  центр `(anchor.x, anchor.y - diameter/2 - 3)`, заливка `#2F8CFF`, текст кегль **11**,
  начертание SemiBold, белый. Отличия от экспортного рендера в кеглях и коэффициентах — намеренные,
  повторить обе формулы отдельно.

### 4.7 Какие файлы попадают в буфер

`PreparedExport.GetImagePathsInOrder()` (`ExportContracts.cs:27-29`) — **абсолютные** пути ко всем
экспортным PNG в порядке manifest, то есть A, B, C. Именно они кладутся в буфер как список файлов,
вместе с `promptText` (§1.10). `prompt.md` и `manifest.json` в буфер **не** кладутся; они попадают
только в ручное сохранение пакета в папку.

## 5. Транспорт: буфер обмена и вставка

Исходная позиция (`tasks/prd-snapbrief.md:170-174`): у Windows нет универсального формата
«три картинки плюс три комментария»; приёмник сам выбирает формат. Отсюда — собственная модель
пакета и несколько проверяемых способов передачи. **Основной сценарий: обычный Ctrl+V/Cmd+V
пользователя**, выбора получателя в интерфейсе нет (`tasks/prd-snapbrief.md:434`).

### 5.1 WindowsClipboardService (`Windows/WindowsClipboardService.cs`)

Служба владеет **собственным STA-потоком** с очередью сообщений (`StaWorkQueue.cs`), потому что
OLE-буфер требует STA. Все операции выполняются на нём (`:22-66`).

Операции:

| Операция | Что делает |
|---|---|
| `CaptureAsync` | снимок текущего содержимого буфера со всеми форматами |
| `SetPackageGuardedAsync(paths, text, expectedSeq)` | записать пакет, только если номер последовательности равен ожидаемому |
| `SetPngGuardedAsync(path, expectedSeq)` | записать одно изображение |
| `SetTextGuardedAsync(text, expectedSeq)` | записать только текст |
| `IsCurrentAsync(receipt)` | номер последовательности всё ещё равен номеру receipt |
| `RestoreIfCurrentAsync(snapshot, receipt)` | восстановить прежнее содержимое, если буфер всё ещё наш |

**Номер последовательности** — `GetClipboardSequenceNumber()` из user32; он монотонно растёт при
любой чужой записи. Receipt = номер **после** нашей записи.

Снятие снимка буфера (`CaptureCore`, `:68-94`): до 5 попыток; в каждой читается номер до, все
форматы без автоконвертации, номер после. Если номер не изменился — снимок валиден.
Формат, который не читается, помечает снимок **неполным**, но не срывает операцию.
Если за 5 попыток номер каждый раз менялся — ошибка «буфер изменён».
Значения клонируются глубоко (`:139-148`): потоки копируются в память, массивы и коллекции строк
дублируются, изображения клонируются и замораживаются.

Запись с защитой (`SetDataObjectWithRetry`, `:98-120`):
1. Если мы ещё не владеем буфером и задан ожидаемый номер — проверить его; несовпадение — ошибка
   «буфер изменён».
2. Записать объект с флагом копирования (это делает содержимое персистентным после выхода процесса).
3. Ошибка «буфер занят» (HRESULT `0x800401D0`) — повторить, задержка `20 * (номер попытки + 1)` мс,
   всего до 5 попыток.
4. **Важная тонкость** (`:112-116`): запись сначала делает нас владельцем, а потом сбрасывает данные.
   Если упал только сброс, служба обнаруживает, что владелец уже она, и повторяет **только сброс**,
   не считая собственный инкремент номера чужой записью. Если после этого владелец сменился —
   ошибка «буфер изменён».

Формирование содержимого:
- одно изображение (`CreatePngDataObject`, `:187-196`): байты файла как формат `PNG`,
  сгенерированный `CF_DIB`, и `CF_BITMAP` с автоконвертацией;
- пакет (`CreatePackageDataObject`, `:198-213`): если путь один — берётся объект одного изображения,
  иначе пустой; затем добавляется список файлов и текст. Пустой список путей — ошибка
  `A clipboard package needs at least one PNG path.`
- DIB (`CreateDib`, `:215-244`): 40-байтный `BITMAPINFOHEADER`, ширина, **положительная** высота
  (строки снизу вверх), 1 плоскость, 32 бита, сжатие `BI_RGB` (0), размер данных, нули в остальных
  полях; далее пиксели BGRA построчно **в обратном порядке строк**.

**macOS-эквивалент.**
- `NSPasteboard.general`; счётчик изменений — `changeCount` (прямой аналог sequence number).
- Guarded-запись: прочитать `changeCount`, сравнить с ожидаемым, затем `clearContents()` (он же
  возвращает новый `changeCount`) и `writeObjects` / `setData(_:forType:)`.
  **Атомарности нет ни там, ни там** — это best-effort, как и на Windows (`Windows/README.md:12`).
- Форматы: несколько файлов — массив `NSURL` (UTI `public.file-url`), текст — `NSPasteboard.PasteboardType.string`,
  одно изображение — `public.png` (сырые байты) плюс `NSImage` через `writeObjects` для приложений,
  читающих `NSImage`. Аналога `CF_DIB` не нужно: на macOS `public.tiff` играет роль
  «универсального растрового формата», его добавлять по желанию.
- STA-поток не нужен; `NSPasteboard` потокобезопасен, но всю работу удобнее вести на главном
  акторе либо в выделенном actor.
- Персистентность после выхода процесса на macOS обеспечивается автоматически: pasteboard хранит
  данные, а не promise, если писать `Data`, а не lazy provider.

### 5.2 PasteCoordinator (`Windows/PasteCoordinator.cs`)

Координатор пошаговой вставки. В основном сценарии он **не используется** (получателя не выбирают),
но он есть в коде, покрыт тестами и остаётся частью контракта.

#### Общая точка входа (`:11-47`)

1. Создать состояние операции: идентификатор экспорта, `SafeResumePrefix` из токена продолжения
   (либо 0), `ImagesConfirmed` и `ImagesDispatched` равны префиксу, `CanResume = true` (`:223-231`).
2. Валидировать профиль (§5.3).
3. Валидировать пакет (`ValidatePackage`, `:180-190`), сообщения:
   - пустой идентификатор экспорта — `У подготовленного пакета отсутствует export ID.`
   - нет изображений — `В пакете нет изображений.`
   - любой путь не абсолютный, не с расширением `.png` или не существует —
     `Все изображения должны быть существующими PNG с абсолютными путями.`
   - пустой текст — `Текст задания пуст.`
   - токен продолжения от другого экспорта, с отрицательным или слишком большим числом
     подтверждённых, или уже с подтверждённым текстом —
     `Точка продолжения не относится к этому экспорту или уже завершена.`
   Любая из этих ошибок даёт статус `InvalidPackage`.
4. Сообщить прогресс: фаза `Validating`, текст `Проверяем пакет, буфер обмена и активное поле.`
5. Снять текущую цель (переднее окно). Если цель непригодна или не соответствует профилю — статус
   `TargetMismatch`, текст `Активное окно не соответствует выбранному профилю.`
6. Снять снимок буфера.
7. Выбрать ветку по транспорту профиля.

Перехваты (`:35-46`):
- «буфер изменён» — статус `ClipboardChanged`, текст
  `Буфер обмена изменён другим приложением. Вставка остановлена без перезаписи новых данных.`
- отмена — статус `Cancelled`, текст
  `Вставка отменена. Проверьте черновик перед повтором; подготовленный экспорт сохранён.`
- прочее — статус `Failed`, текст
  `Не удалось выполнить вставку. Проверьте черновик перед повтором; подготовленный экспорт сохранён.`

#### Ветка SingleClipboardPackage (`:49-85`)

```

прогресс PreparingClipboard, "Копируем отдельные PNG и текст в один буферный пакет."
записать пакет с защитой по номеру исходного буфера
проверка после записи (см. ниже)

ImagesDispatched = число изображений ; TextDispatched = true

    любой TargetLost   -> TargetChanged,      "Активное окно или поле ввода изменилось во время ожидания."
    любой TimedOut     -> AcceptanceTimedOut, "Получатель не подтвердил весь пакет вовремя. Проверьте черновик перед повтором."

TextConfirmed   = текст Accepted

```

Тексты завершения:
- verified: `Все отдельные вложения и текст подтверждены получателем. Запрос оставлен черновиком.`
- иначе: `Комбинация вставки отправлена; весь пакет нельзя проверить автоматически. Проверьте черновик. Запрос не отправлен.`

#### Ветка StagedSequence (`:87-158`)

```
expectedSequence = номер исходного буфера
для index от SafeResumePrefix до количества изображений:
    проверить цель -> не та: TargetChanged

Тексты завершения:
- verified: `Все изображения и текст подтверждены получателем. Запрос оставлен черновиком.`
- иначе: `Все комбинации вставки отправлены; часть приёма нельзя проверить автоматически. Проверьте черновик. Запрос не отправлен.`

Остановка по неподтверждению (`StopForAcceptance`, `:173-178`):
- `TimedOut` — статус `AcceptanceTimedOut`, текст
  `Получатель не подтвердил приём вовремя. Проверьте черновик перед повтором.`
- иначе — статус `TargetChanged`, текст
  `Активное окно или поле ввода изменилось во время ожидания.`

#### Проверка после записи (`CheckAfterWriteAsync`, `:163-171`)

Выполняется **после каждой** записи в буфер и **после каждого** ожидания:
1. Проверить отмену.
2. Проверить, что цель та же; иначе `TargetChanged`.
3. Проверить, что буфер всё ещё наш; иначе `ClipboardChanged` с текстом
   `Буфер обмена изменён другим приложением. Вставка остановлена без перезаписи новых данных.`

#### Таймауты (`:192-215`)

Каждое ожидание оборачивается в связанный токен отмены с `CancelAfter(profile.AcceptanceTimeout)`.
Отмена **по таймауту** (а не пользователем) превращается в `TimedOut`.
Для пакетного ожидания таймаут даёт `(TimedOut, TimedOut)`.

#### Токен продолжения (`:241-247`)

Токен выдаётся, **только если** `CanResume` истинно, `SafeResumePrefix > 0` и текст ещё не
подтверждён. То есть после любого неподтверждаемого шага безопасное продолжение недоступно —
пользователь обязан посмотреть черновик (`Windows/README.md:16`).

#### Полная машина состояний

Фазы (`PastePhase`, `TransportContracts.cs:239-249`): `Validating`, `PreparingClipboard`,
`SendingImage`, `WaitingForImage`, `SendingText`, `WaitingForText`, `Completed`, `Stopped`.

Итоговые статусы (`PasteStatus`, `:260-271`): `CompletedVerified`, `CompletedUnverified`,
`InvalidPackage`, `TargetMismatch`, `TargetChanged`, `ClipboardChanged`, `AcceptanceTimedOut`,
`Cancelled`, `Failed`.

Переходы:

```
Validating --(пакет невалиден)--------------------> InvalidPackage      [конец]
Validating --(окно не по профилю)-----------------> TargetMismatch      [конец]
Validating --> PreparingClipboard

PreparingClipboard --(чужая запись)---------------> ClipboardChanged    [конец]
PreparingClipboard --(смена окна/фокуса)----------> TargetChanged       [конец]
PreparingClipboard --> SendingImage

SendingImage --> WaitingForImage
WaitingForImage --(Accepted)---------------------> следующее изображение либо SendingText
WaitingForImage --(NotObservable)----------------> то же, но CanResume = false
WaitingForImage --(TimedOut)---------------------> AcceptanceTimedOut   [конец]
WaitingForImage --(TargetLost)-------------------> TargetChanged        [конец]

SendingText --> WaitingForText
WaitingForText --(Accepted)----------------------> Completed
WaitingForText --(NotObservable)-----------------> Completed, CanResume = false
WaitingForText --(TimedOut)----------------------> AcceptanceTimedOut   [конец]
WaitingForText --(TargetLost)--------------------> TargetChanged        [конец]

Completed --(всё Accepted)-----------------------> CompletedVerified
Completed --(иначе)------------------------------> CompletedUnverified

в любой момент: отмена ------------------------> Cancelled
в любой момент: прочее исключение --------------> Failed
```

**Enter не отправляется никогда, ни в одной ветке** (`PRODUCT.md:41`).

`PasteResult` (`TransportContracts.cs:275-286`) несёт: статус, сколько изображений отправлено,
сколько подтверждено, отправлен ли текст, подтверждён ли текст, токен продолжения, сообщение
и опциональную ошибку. `DeliveryWasObserved` истинно **только** при `CompletedVerified`.

### 5.3 TargetProfile и встроенные профили (`Windows/TransportContracts.cs`)

`HotkeyModifiers` (`:8-17`) — битовые флаги, значения обязательны к сохранению, потому что они
попадают в идентификаторы сочетаний (§7.2): `None = 0`, `Alt = 1`, `Control = 2`, `Shift = 4`,
`Windows = 8`, `NoRepeat = 0x4000`.

`HotkeyGesture(Modifiers, VirtualKey)` (`:19-28`): готовые значения `CtrlV` = Control + `0x56`,
`CtrlShiftV` = Control + Shift + `0x56`, `AltV` = Alt + `0x56`. Константа `EnterVirtualKey = 0x0D`
и свойство «содержит Enter».

`TargetProfile` (`:43-69`): `Id`, `DisplayName`, `Transport`, `ImagePasteGesture`,
`TextPasteGesture`, `AllowedProcessNames` (регистронезависимое множество), `AcceptanceTimeout`,
`UnobservableSettlementDelay`, `Verification`, `VerifiedVersion`, `RestoreClipboardWhenSafe`.

Валидация профиля (`:55-68`), точные сообщения:
- пустой идентификатор или имя — `A target profile needs an id and display name.`
- любой из жестов содержит Enter — `Paste profiles must never contain Enter.`
- транспорт `SingleClipboardPackage`, но жесты изображения и текста разные —
  `A single clipboard package must use one shared paste gesture.`
- пустое множество процессов — `A target profile needs at least one allowed process name.`
- неположительный таймаут приёма или отрицательная задержка — ошибка диапазона.

Встроенные профили (`:71-147`), все со статусом **Unverified**, таймаут **8 секунд**,
задержка «неподтверждаемости» **900 мс**:

iTerm2, VS Code. Жест вставки изображения на macOS — `Cmd+V`; терминальные клиенты Claude Code
используют `Alt+V` (Option+V) — это надо перепроверить для macOS-сборки CLI отдельно.

### 5.4 CodexDesktopPasteCompletionService (`Windows/CodexDesktopPasteCompletionService.cs`)

**Назначение.** Практическая проверка показала (`tasks/verification.md:17`): Codex Desktop
принимает PNG из буфера, но **игнорирует текст из того же буфера**. Поэтому после физического
Ctrl+V пользователя выполняется охраняемый второй шаг: подождать, проверить всё, положить в буфер
**только текст** и повторить Ctrl+V. Enter не отправляется.

Задержка по умолчанию — **500 мс** (`:5`).

Алгоритм (`:25-108`):

1. **Синхронно, до первого ожидания** (комментарий `:34-35`) снять текущую цель — чтобы
   зафиксировать сфокусированный элемент в момент физического нажатия, а не после задержки.
2. Отказ со статусом `NotApplicable` и сообщением
   `Paste completion applies only to a physical Ctrl+V in Codex Desktop.`, если:
   - гест не Ctrl+V (например, Alt+V);
   - цель непригодна;
   - дескриптор окна не совпадает с зафиксированным в намерении;
   - идентификатор процесса не совпадает;
   - процесс не входит в профиль Codex Desktop.
3. Если номер последовательности буфера в намерении не равен номеру нашего пакета — статус
   `StaleIntent`, сообщение `The paste intent does not refer to SnapBrief current package.`
4. Если текст задания пуст — статус `NothingToDispatch`, сообщение
   `The package has no prompt text to paste.`
5. Подождать 500 мс.
6. Если буфер уже не наш — статус `ClipboardChanged`, сообщение
   `The clipboard changed before the text paste.`
7. Если цель сменилась — статус `TargetLost`, сообщение
   `Codex focus changed before the text paste.`
8. Записать **только текст** в буфер с защитой по номеру нашего пакета. Получить новый receipt.
9. Отправить Ctrl+V **через охраняемую инъекцию**: инжектор сначала ждёт физического отпускания
   клавиш (§5.6), а **непосредственно перед** самой инъекцией вызывает финальную проверку:
   - буфер всё ещё содержит наш текст — иначе отказ со статусом `ClipboardChanged` и сообщением
     `The clipboard changed while the paste keys were being released.`;
   - цель та же — иначе отказ со статусом `TargetLost` и сообщением
     `Codex focus changed while the paste keys were being released.`
10. Успех — статус `CompletedUnverified`, сообщение
    `Prompt text paste was dispatched to Codex; receiver acceptance was not observable.`

Исключения: «буфер изменён» — `ClipboardChanged` с сообщением исключения; отмена — `Cancelled`
с `The guarded text paste was cancelled.`; прочее — `Failed` с `The guarded text paste failed: {msg}`.

Во всех ветках после шага 8 в результат возвращается receipt записанного текста, даже если
инъекция не состоялась — вызывающая сторона обязана обновить своё представление о владении буфером
(`EdgeStackWindow.xaml.cs:208-209`).

Статусы (`TransportContracts.cs:321-331`): `CompletedUnverified`, `NotApplicable`,
`NothingToDispatch`, `StaleIntent`, `TargetLost`, `ClipboardChanged`, `Cancelled`, `Failed`.
`TextWasDispatched` истинно **только** при `CompletedUnverified`.

**Результат называется CompletedUnverified осознанно** (`tasks/verification.md:19`):
задержка и отправка клавиш не доказывают приём изображения или текста.

### 5.5 WindowsForegroundTargetService (`Windows/WindowsForegroundTargetService.cs`)

`Capture()` (`:9-24`) собирает `TargetSnapshot(WindowHandle, FocusedControlHandle, ProcessId,
ProcessName, WindowTitle)`:
- дескриптор переднего окна; если его нет — пустой снимок;
- идентификатор потока и процесса окна;
- имя процесса; при ошибке — пустая строка;
- заголовок окна;
- **дескриптор сфокусированного дочернего элемента** через `GetGUIThreadInfo` для потока окна;
  если информация недоступна — 0.

`IsSame(expected)` (`:26-32`): заново снять цель и сравнить **дескриптор окна, дескриптор
сфокусированного элемента и идентификатор процесса**. Заголовок окна в сравнение **не входит**.

`Matches(target, profile)` (`:34-35`): имя процесса входит в множество профиля (регистронезависимо).

`IsUsable` (`TransportContracts.cs:177`): дескриптор окна не 0 и идентификатор процесса не 0.

Когда Windows не отдаёт дескриптор сфокусированного дочернего элемента, защита деградирует до
сравнения окна верхнего уровня (`Windows/README.md:12`) — это ожидаемое поведение, не ошибка.

**macOS-эквивалент.**
- Переднее приложение — `NSWorkspace.shared.frontmostApplication`, даёт `processIdentifier`,
  `bundleIdentifier`, `localizedName`.
- Дескриптор окна и заголовок — только через Accessibility API (`AXUIElementCreateApplication`,
  атрибут `kAXFocusedWindowAttribute`, `kAXTitleAttribute`) либо через `CGWindowListCopyWindowInfo`
  (последний даёт номер окна и заголовок **без** Accessibility, но требует Screen Recording для
  чтения заголовков на новых macOS).
- Сфокусированный элемент — `kAXFocusedUIElementAttribute`, **требует TCC Accessibility**.
- Практический минимум без Accessibility: сравнивать `processIdentifier` плюс номер переднего окна
  из `CGWindowListCopyWindowInfo` с `kCGWindowLayer == 0`. Это слабее Windows-версии; расхождение
  зафиксировать (§9.3).

### 5.6 Инъекция клавиш (`Windows/WindowsInputInjector.cs`)

- **Enter отвергается на нативной границе** (`:44`): попытка отправить Enter — исключение
  `SnapBrief never injects Enter.` Это второй рубеж после валидации профиля.
- Перед инъекцией ждём физического **отпускания** клавиш: Control, Shift, Alt, левый Win, правый Win
  и сама клавиша жеста (`:61-70`). Опрос каждые 10 мс, таймаут по умолчанию **750 мс**; при
  превышении — исключение `Paste shortcut keys or trigger modifiers are still physically held.`
  Смысл: глобальный триггер не должен «протечь» модификаторами в целевое сочетание;
  синтетический key-up для удерживаемой пользователем клавиши **никогда не генерируется**
  (`Windows/README.md:18`).
- Если задана финальная проверка (охраняемый режим) — она вызывается **после** ожидания отпускания
  и **непосредственно перед** инъекцией; отказ означает «не отправлено» без исключения (`:46`).
- Последовательность событий (`:48-53`): нажатия модификаторов в порядке Control, Shift, Alt,
  левый Win; затем нажатие клавиши; затем её отпускание; затем отпускания модификаторов
  **в обратном порядке**.
- Если система приняла не все события — исключение
  `Windows rejected part of the paste shortcut, possibly because the target has a higher integrity level.`
- Опрос физического состояния — `GetAsyncKeyState`, старший бит.

**macOS-эквивалент.** `CGEvent(keyboardEventSource:virtualKey:keyDown:)` плюс `flags`,
`post(tap: .cghidEventTap)`. Требуется TCC **Accessibility** (Input Monitoring нужен для
**чтения** событий, Accessibility — для их **генерации**). Проверка физического состояния клавиш —
`CGEventSource.keyState(.combinedSessionState, key:)`. Виртуальные коды — из `Carbon.HIToolbox`
(`kVK_ANSI_V = 0x09`, `kVK_Command = 0x37`, `kVK_Shift = 0x38`, `kVK_Option = 0x3A`,
`kVK_Control = 0x3B`, `kVK_Return = 0x24`). Запрет на Return сохранить.

### 5.7 UnobservableAcceptanceObserver (`Windows/UnobservableAcceptanceObserver.cs`)

Наблюдатель по умолчанию, который **честно признаёт, что не может наблюдать приём**:

- ждёт `profile.UnobservableSettlementDelay` (900 мс у встроенных профилей);
- если цель после ожидания та же — возвращает `NotObservable`, иначе `TargetLost`;
- для пакетного ожидания возвращает **одинаковый** исход для изображений и текста.

Ключевое следствие: успешное завершение через этот наблюдатель всегда даёт `CompletedUnverified`,
**никогда** `CompletedVerified` (`Windows/README.md:16`). Будущий наблюдатель на базе UI Automation
может возвращать `Accepted`, только если реально увидел вложение или текст в получателе.

`AcceptanceOutcome` (`TransportContracts.cs:210-216`): `Accepted`, `NotObservable`, `TimedOut`,
`TargetLost`.

**macOS-эквивалент.** Тот же честный наблюдатель по умолчанию. Наблюдение приёма возможно только
через Accessibility (дерево элементов композера получателя) и требует отдельной проверки на каждой
версии приложения — реализовывать не в первой версии.

### 5.8 Наблюдение намерения вставки: macOS

Windows-версия ставит глобальный низкоуровневый клавиатурный хук (§1.11). На macOS эквивалент —
`CGEvent.tapCreate(tap: .cgSessionEventTap, place: .headInsertEventTap, options: .listenOnly,
eventsOfInterest: keyDown | keyUp | flagsChanged, callback:)`, добавленный в run loop.

Обязательные соответствия:
- `options: .listenOnly` — мы **только слушаем**, не модифицируем и не глотаем события;
- фильтр инъецированных событий: у Windows это флаг `LLKHF_INJECTED`; на macOS проверять
  `event.getIntegerValueField(.eventSourceUserData)` с собственной меткой, которую мы ставим
  при своей инъекции, **и/или** `.eventSourceStateID`. Это обязательный аналог, иначе
  собственная инъекция Cmd+V вызовет рекурсию;
- распознавать **Cmd+V** и **Option+V** (аналоги Ctrl+V и Alt+V), с теми же правилами:
  ровно один из Cmd и Option, отсутствие Shift и Control, гашение авто-повтора;
- события от собственного процесса отбрасывать по `pid` из
  `event.getIntegerValueField(.eventTargetUnixProcessID)`;
- снимать `NSPasteboard.general.changeCount` в момент события;
- обработчик обязан быть невыбрасывающим и максимально коротким.

**Требуется TCC Input Monitoring** (`kTCCServiceListenEvent`). Без разрешения `tapCreate` вернёт nil.
Поведение при отказе повторяет Windows: статус **«Отслеживание вставки недоступно: {причина}»**
(`EdgeStackWindow.xaml.cs:161`), приложение продолжает работать, но не ротирует сессию по вставке —
остаётся ручной пункт «Новая сессия» и проверка буфера перед следующим захватом (§1.12).

#### Размещение изображения (`FitRect`, `:474-481`)

```
availW = max(1, width  - padding * 2)
availH = max(1, height - padding * 2)
scale  = min(availW / imageWidth, availH / imageHeight)
w = imageWidth * scale ; h = imageHeight * scale
rect = ((width - w) / 2, (height - h) / 2, w, h)
```

#### Порядок отрисовки (`OnRender`, `:94-112`)

1. Белый прямоугольник под изображением.
2. Изображение со всеми применёнными blur.
3. Все отметки, **кроме Blur и Conceal**, — только формы, без подписей.
4. Отметки **Conceal** — только формы, поверх остального.
5. **Все** отметки — только рамка выделения и подписи, без форм.
6. Если тянут blur — чёрный прямоугольник с синим контуром толщиной 1.5 на его месте.
7. Черновик текущего жеста — полностью, включая подпись.

То есть подписи-номера всегда поверх форм.

#### Отрисовка формы на экране (`DrawAnnotation`, `:328-415`)

Перевод точки изображения в экран: `target.X + p.x * target.Width / imageWidth`, аналогично по Y.
`scale = target.Width / imageWidth`; **толщина пера на экране** равна `max(1.5, Thickness * scale)`.
Это отличается от экспорта, где толщина берётся без масштабирования.

| Вид | Отрисовка |
|---|---|
| Pen и Highlight | линии по всем сегментам; для Highlight альфа `0.35 * 255` и толщина x4 |
| Rectangle | контур, перо цвета отметки |
| Conceal | сплошная чёрная заливка |

Подпись-номер: `diameter = max(26, длина_метки * 7 + 12)`, центр `(anchor.x, anchor.y - diameter/2 - 3)`,

#### Взаимодействие

- Нажатие вне прямоугольника изображения игнорируется (`:120`).
- Сначала ищется попадание в **угловую ручку** (`:300-315`, радиус 10 DIP): сперва у выделенной
  отметки, затем у всех остальных в обратном порядке.
- Если активен Select **или** попали в ручку — выделить найденную отметку и начать манипуляцию
  (перенос либо изменение размера), захватив мышь.
- Иначе начать новый черновик: вид равен активному инструменту, цвет равен активному
  (для Conceal принудительно чёрный), толщина равна активной, две точки в позиции нажатия.
- Hit-test отметки (`:316-326`): прямоугольник отметки, раздутый на `max(8, Thickness * 2)`
  по обеим осям; обратный порядок перебора, верхняя выигрывает.
- Перемещение: смещение зажимается так, чтобы отметка не вышла за границы изображения (`:176-177`);
  двигаются **все** точки и все дополнительные сегменты.
- Изменение размера: новый прямоугольник через `ResizeGeometry.Resize` (минимум **2** пикселя,
  лимит — изображение), все точки переносятся пропорционально через `ResizeGeometry.Map`.
- Курсор при наведении без нажатия (`:189-192`): над ручкой — диагональный (NWSE для углов 0 и 2,
  NESW для 1 и 3), иначе стрелка при Select и перекрестие при остальных инструментах.
- Для Pen и Highlight каждое движение **добавляет** точку; для остальных обновляется вторая точка.
- Точка всегда зажимается в границы изображения.
- Отпускание: если жест имеет размер (§1.3) — либо запрос обрезки для Crop, либо добавление
  отметки, её выделение и событие «создана».
- **Delete** удаляет выделенную отметку и вызывает событие изменения, то есть попадает в undo.
- **Escape** отменяет текущий черновик (`:246-253`).
- Смена коллекции отметок сбрасывает выделение (`:83-90`).

## 7. Горячие клавиши

### 7.1 Регистрация (`Windows/WindowsGlobalHotkeyService.cs`)

- Служба привязана к дескриптору созданного окна и подписывается на его оконную процедуру (`:17-23`).
- Идентификаторы регистрации выдаются последовательно начиная с `0x4000` (`:14`, `:32`).
- Регистрация именованного сочетания (`:27-37`): пустое имя — ошибка `A hotkey id is required.`;
  повторная регистрация того же имени — ошибка `Hotkey {id} is already registered.`;
  отказ системы — исключение с сообщением `Could not register global hotkey {id}.`
  и **кодом ошибки Windows**, например 1409.
- Снятие регистрации (`:39-44`) идемпотентно: неизвестное имя молча игнорируется.
- Сообщение `WM_HOTKEY` равно `0x0312`; при совпадении идентификатора событие помечается
  обработанным и поднимается событие «нажата клавиша с именем» (`:46-54`).
- Освобождение снимает все регистрации и отписывается (`:56-64`).

Имена, используемые приложением: `capture` и `fullscreen-save` (`EdgeStackWindow.xaml.cs:167-168`).

Флаг `NoRepeat` (`0x4000`) входит **во все** пресеты и во все пользовательские сочетания
(`HotkeySettingsWindow.xaml.cs:31-37`, `:73`): авто-повтор при удержании не порождает повторных
срабатываний.

### 7.2 Формат хранения сочетания

Сочетание хранится **строкой-идентификатором**. Два вида (`HotkeySettingsWindow.xaml.cs:57-76`).

**А. Пресет** — одно из семи фиксированных имён:

| Id | Метка | Модификаторы | VK |
|---|---|---|---|
| `ctrl-alt-s` | `Ctrl + Alt + S` | Control, Alt, NoRepeat | `0x53` |
| `ctrl-shift-s` | `Ctrl + Shift + S` | Control, Shift, NoRepeat | `0x53` |
| `alt-s` | `Alt + S` | Alt, NoRepeat | `0x53` |
| `print-screen` | `Print Screen` | NoRepeat | `0x2C` |
| `ctrl-alt-v` | `Ctrl + Alt + V` | Control, Alt, NoRepeat | `0x56` |
| `ctrl-shift-v` | `Ctrl + Shift + V` | Control, Shift, NoRepeat | `0x56` |
| `alt-v` | `Alt + V` | Alt, NoRepeat | `0x56` |

Список сочетаний для вставки — те же семь **без** `print-screen` (`:39-40`).

**Б. Пользовательское сочетание** — строка вида `custom:{модификаторы}:{виртуальная клавиша}`,
где модификаторы — десятичное число из битов `Alt = 1`, `Control = 2`, `Shift = 4`, `Windows = 8`.
Примеры: `custom:4:44` равно Shift плюс Print Screen; `custom:6:75` равно Control плюс Shift плюс K;
`custom:0:19` равно Pause/Break без модификаторов.

Разбор пользовательской строки (`:61-74`) принимает её, только если:
- ровно три части, первая равна `custom`;
- модификаторы и клавиша разбираются как беззнаковые числа;
- клавиша строго больше 0 и строго меньше 255;
- в модификаторах **нет** битов вне маски 15.

Иначе **возвращается первый пресет** `ctrl-alt-s` — проверенный fallback для повреждённых
и незнакомых значений (`:75`, smoke-проверка со строкой `custom:999:13`).

Метка пользовательского сочетания собирается в фиксированном порядке:
`Ctrl + `, `Alt + `, `Shift + `, `Win + `, затем имя клавиши. Имя клавиши:
`0x13` даёт `Pause / Break`, `0x2C` даёт `Print Screen`, остальные — стандартное имя клавиши.
К результату **всегда** добавляется флаг `NoRepeat` (`:73`).

### 7.3 Запись сочетания в поле настроек

Поля записи — только для чтения; ввод перехватывается на уровне предпросмотра событий клавиатуры
(`HotkeySettingsWindow.xaml:24`, `:26`).

Начало записи (`:108-115`): получение клавиатурного фокуса **или** нажатие мышью по полю.
Поле показывает **`Нажмите клавишу…`**, строка ошибки скрывается.

Обработка нажатия (`OnCaptureKeyDown`, `:124-130`):
- если запись не идёт — ничего;
- событие всегда помечается обработанным, то есть **Tab, Enter и Escape во время записи
  не выполняют навигацию**;
- системная клавиша разворачивается в реальную; IME-обработанная — в исходную;
- если это **не** чистый модификатор — записать сочетание.

Обработка отпускания (`OnCaptureKeyUp`, `:117-123`):
- событие всегда помечается обработанным;
- **на отпускании** записываются: `Pause`, `Print Screen` (они не дают нормального нажатия)
  и **чистые модификаторы**, то есть можно назначить одиночный Ctrl, Shift, Alt или Win.

Запись (`RecordKey`, `:131-145`):
- виртуальный код вне диапазона 1..254 игнорируется;
- модификаторы берутся из **текущего** состояния клавиатуры;
- собирается строка `custom:{модификаторы}:{vk}`;
- строка присваивается тому полю, которое сейчас записывает;
- поле показывает человекочитаемую метку;
- **режим записи завершается, и фокус переходит на кнопку «Сохранить»** (`:144`).

Требование пользователя (`tasks/prd-snapbrief.md:452`): один клик, одно нажатие, сохранение;
пока поле записывает, Enter, Tab и Escape относятся к назначению, а не к навигации; после записи
фокус переходит на сохранение; модификаторы поддерживаются и в сочетании, и по отдельности.

**Важно:** искусственное исключение Enter из назначения глобальной клавиши было **удалено**
(`tasks/verification.md:94`) — назначить Enter клавишей захвата можно, это не связано с запретом
отправлять Enter агенту. Запрет на **инъекцию** Enter (§5.6) остаётся.

Историческая заметка `tasks/verification.md:80` («Tab и Escape остаются навигацией») относится
к более ранней версии; действующий код (`:124-130`) помечает обработанными **все** клавиши
во время записи.

### 7.4 Проверка конфликтов

- Возможность глобальной регистрации проверяет система; отказ показывается **внутри** диалога
  настроек, прежнее назначение сохраняется при отмене (`tasks/prd-snapbrief.md:452`).
- Перед открытием диалога обе клавиши **снимаются с регистрации** — иначе собственное сочетание
  выглядело бы занятым (`EdgeStackWindow.xaml.cs:552-553`).
- При сохранении новые сочетания регистрируются **до** закрытия диалога; ошибка оставляет диалог
  открытым с конкретным текстом (§1.17).
- Конфликт 1409 подтверждён на реальной машине (`tasks/verification.md:99`).
- Никогда не перехватывать системный `Win+Shift+S` без отдельной настройки
  (`tasks/prd-snapbrief.md:119`). Существующие сочетания Windows и Lightshot автоматически
  не изменяются (FR-22, `tasks/prd-snapbrief.md:164`).

### 7.5 Внутренние клавиши редактора (`OverlayEditorWindow.xaml.cs:729-764`)

Приоритет обработки:
1. **Ctrl+S** — сохранить снимок в файл; проверяется первым, до проверки фокуса в поле.
2. Если фокус в текстовом поле: **Escape** снимает фокус на холст, всё остальное — обычный ввод
   текста; Ctrl+C внутри поля — обычное копирование.
3. **Escape** вне поля — отмена: временные файлы удаляются, результат помечается отменённым,
   окно закрывается. Для нового снимка возвращается пусто, для существующего — неизменённый снимок.
4. **Ctrl+Z** — Undo, **Ctrl+Y** — Redo.
5. **Ctrl+C** при наличии снимка — завершить снимок.
6. Без модификаторов — переключение инструмента:
   `V` Select, `R` Rectangle, `A` Arrow, `B` Blur, `C` Crop, `P` Pen, `H` Highlight, `T` Text,
   `X` Conceal.
7. **Delete** внутри холста удаляет выделенную отметку (`AnnotationCanvas.cs:238-245`).

### 7.6 Маппинг на macOS

Общее правило: **Ctrl заменяется на Command**, Alt остаётся Option.

| Действие | Windows | macOS |
|---|---|---|
| Глобальный захват области | Ctrl+Alt+S | **Cmd+Option+S** |
| Глобальное быстрое сохранение экрана | Shift+Print Screen, выключено | предложить **Shift+Cmd+Option+S**, выключено по умолчанию; см. §10 |
| Сохранить снимок в файл | Ctrl+S | **Cmd+S** |
| Завершить снимок | Ctrl+C | **Cmd+C** |
| Undo | Ctrl+Z | **Cmd+Z** |
| Redo | Ctrl+Y | **Shift+Cmd+Z** — принятая на macOS форма |
| Отмена | Esc | Esc |
| Удалить отметку | Delete | Delete или Backspace |
| Инструменты | V R A B C P H T X | те же, без модификаторов |
| Наблюдаемая вставка пользователя | Ctrl+V, Alt+V | **Cmd+V**, **Option+V** |

**Регистрация глобальных клавиш на macOS.** Два варианта:

1. **Carbon `RegisterEventHotKey`** из `Carbon.HIToolbox` — работает **без TCC-разрешений**,
   прямой аналог `RegisterHotKey`. Даёт `EventHotKeyRef`, обработчик ставится через
   `InstallEventHandler` на класс `kEventClassKeyboard` и тип `kEventHotKeyPressed`.
   API формально устаревшее, но поддерживается и остаётся единственным способом без Accessibility.
   **Вариант по умолчанию.**
2. `CGEvent` tap — гибче, ловит любые комбинации, включая одиночные модификаторы,
   но **требует TCC Accessibility или Input Monitoring**.

Практическое следствие: «одиночный модификатор как горячая клавиша» (§7.3 это разрешает на Windows)
через Carbon **невозможен**. Если такая возможность нужна, она реализуется поверх того же event tap,
который уже нужен для детекта вставки (§5.8), и становится зависимой от Input Monitoring.
Рекомендация: пресеты и обычные сочетания — через Carbon; одиночные модификаторы — только если
event tap уже разрешён, иначе показывать в настройках сообщение об ограничении.

Конфликт регистрации: Carbon возвращает `eventHotKeyExistsErr` (значение -9878).
Это прямой аналог 1409, показывать то же сообщение
**«Эта клавиша уже занята. Освободите её в другом приложении или выберите другую.»**

Соответствие модификаторов Carbon: `cmdKey = 0x0100`, `shiftKey = 0x0200`, `optionKey = 0x0800`,
`controlKey = 0x1000`. Виртуальные коды: `kVK_ANSI_S = 0x01`, `kVK_ANSI_V = 0x09`,
`kVK_Escape = 0x35`, `kVK_Return = 0x24`.

Формат хранения (§7.2) сохранить **как есть**, чтобы файлы настроек оставались взаимно читаемыми.
Биты модификаторов трактовать так: `Alt = 1` — Option, `Control = 2` — Command, `Shift = 4` — Shift,
`Windows = 8` — Control. Такое отображение и дефолт `ctrl-alt-s` превращает в осмысленное
`Cmd+Option+S`, и сохраняет совместимость файла настроек. Отображение задокументировать в коде
рядом с разбором строки.

## 9. Единичные различия Windows и macOS

Каждое различие сопровождается решением. Там, где 1:1 невозможно, зафиксировано, **что именно**
теряется; это должно попасть в README macOS-порта.

### 9.1 Захват экрана требует TCC Screen Recording

Windows снимает рабочий стол через GDI без разрешений. macOS с 10.15 требует
**Screen Recording** (`kTCCServiceScreenCapture`), а с macOS 14 захват идёт только через
ScreenCaptureKit; `CGWindowListCreateImage` и `CGDisplayCreateImage` устарели и без разрешения
возвращают только обои.

**Решение.** При первом запуске проверить `CGPreflightScreenCaptureAccess()`; если нет —
вызвать `CGRequestScreenCaptureAccess()` и показать в стопке статус с кнопкой открытия
раздела Privacy and Security, Screen Recording. Без разрешения захват отключён, но остальное
приложение (импорт файлов, импорт из буфера, редактирование, экспорт) работает.
Формулировка статуса по образцу существующих: **«Захват: нет разрешения на запись экрана»**.

**Дополнительно.** После выдачи разрешения macOS требует перезапуск приложения. Обработать явно:
предложить перезапуск, а не молча оставаться в нерабочем состоянии.

### 9.2 Наблюдение вставки требует TCC Input Monitoring

Низкоуровневый хук клавиатуры на Windows не требует разрешений. На macOS `CGEvent.tapCreate`
требует **Input Monitoring** (`kTCCServiceListenEvent`).

**Решение.** Проверять `CGPreflightListenEventAccess()`, запрашивать `CGRequestListenEventAccess()`.
При отказе поведение уже определено существующим кодом: статус
**«Отслеживание вставки недоступно: {причина}»** (`EdgeStackWindow.xaml.cs:161`), приложение
продолжает работать. Деградация: сессия не ротируется автоматически после вставки; пользователь
ротирует её вручную пунктом «Новая сессия», а автоматическая проверка буфера перед следующим
захватом (§1.12) всё равно начинает новую сессию, если наш пакет уже не в буфере.
**Основной сценарий при этом остаётся рабочим.**

### 9.3 Инъекция клавиш и определение сфокусированного элемента требуют Accessibility

Windows-версия использует `SendInput` и `GetGUIThreadInfo` без разрешений.
На macOS `CGEvent.post` требует **Accessibility** (`kTCCServiceAccessibility`), и получение
сфокусированного элемента чужого приложения — тоже.

**Решение.**
- Проверять `AXIsProcessTrustedWithOptions` с опцией показа подсказки.
- Без Accessibility **отключить** Codex-догон текста (§5.4) и координатор пошаговой вставки (§5.2).
  Оба не входят в основной сценарий, поэтому потеря приемлема.
- Без Accessibility определение цели деградирует до `NSWorkspace.frontmostApplication`
  плюс номер переднего окна из `CGWindowListCopyWindowInfo`, без сфокусированного элемента.
  Это ослабляет защиту «фокус не сменился» — но и на Windows так бывает, когда дочерний дескриптор
  недоступен (`Windows/README.md:12`), то есть поведение остаётся в рамках описанного контракта,
  просто чаще.

### 9.4 Автозапуск

Windows: запись в реестре. macOS: **`SMAppService.mainApp`** (macOS 13+).

```
включено  = SMAppService.mainApp.status == .enabled
включить  = try SMAppService.mainApp.register()
выключить = try SMAppService.mainApp.unregister()
```

Различия, которые надо принять:
- нельзя проверить, что запись указывает именно на **этот** экземпляр (на Windows сравнивается
  точная командная строка) — система привязывает регистрацию к бандлу;
- `register()` может бросить, если приложение не подписано или лежит вне `/Applications`;
  ошибку показывать тем же статусом **«Не удалось изменить автозапуск: {ошибка}»**;
- пользователь может отключить пункт в General, Login Items, минуя приложение; поэтому состояние
  галочки **перечитывать при каждом открытии меню**, как уже делается на Windows (`:90-95`).

Подпись меню — **«Запускать при входе»** (§1.20).

### 9.5 Система координат экранов

Windows: виртуальный рабочий стол — прямоугольник в пикселях, ось Y вниз, начало в левом-верхнем
углу главного монитора, отрицательные координаты возможны.
macOS: ось Y **вверх**, начало в левом-нижнем углу главного экрана, координаты в **точках**,
не в пикселях; масштаб задаётся `backingScaleFactor` для каждого экрана отдельно.

**Решение.** Ввести один явный слой преобразования:

```
globalRect = объединение всех NSScreen.frame                  (точки, Y вверх)
flip(p)    = (p.x - globalRect.minX, globalRect.maxY - p.y)   (точки, Y вниз, начало 0,0)
pixels(p)  = flip(p) * scale                                  (пиксели кадра)
```

Кадр захвата собирается в **пикселях** и дальше трактуется ровно как `DesktopFrame` на Windows:
`Left`, `Top`, `PixelWidth`, `PixelHeight`, где `Left` и `Top` — координаты в перевёрнутой системе.
После этого **вся** остальная математика спеки (§1, §2, §6) работает без изменений.

Смешанный масштаб экранов: захват через ScreenCaptureKit делается **по каждому дисплею отдельно**;
кадры либо собираются в один битмап в пикселях с наибольшим масштабом, либо кадр строится только
для того дисплея, где идёт выделение. Второй вариант проще и достаточен.
**Выбор зафиксировать и проверить на реальной двухэкранной конфигурации** (§10).

### 9.6 Single instance

Windows: именованный мьютекс плюс named pipe с точным протоколом. На macOS мьютекса нет.

**Решение.** Полагаться на систему: одиночность приложения-бандла обеспечивает Launch Services при
запуске из Finder или через `open`. Для явной проверки —
`NSRunningApplication.runningApplications(withBundleIdentifier:)`: если найден другой экземпляр,
активировать его и завершиться.

Канал активации (аналог команды показа): `DistributedNotificationCenter.default()` с именем
`com.snapbrief.activation.show`. Ограничение доступа текущим пользователем обеспечивается сессией;
проверять поле объекта на фиксированное значение, как Windows-версия проверяет точные 5 байт.

Таймауты Windows-версии (250 мс попытка, 2 с бюджет, 1 с обмен) не нужны: уведомления
доставляются асинхронно и **без подтверждения**. Это расхождение: второй экземпляр не узнает,
дошла ли команда. Компенсация: если через 500 мс другой экземпляр не активировался
(`NSRunningApplication.isActive`), просто завершиться молча — как и на Windows при недоступном
слушателе.

Тест 25 заменяется на проверку, что обработчик реагирует только на точное имя уведомления
и точное значение объекта.

### 9.7 Трей и menu bar

Windows: иконка трея с меню, двойным кликом и всплывающими подсказками.
macOS: `NSStatusItem` в menu bar.

Расхождения и решения:
- **двойной клик не различается** — одиночный левый клик показывает стопку, правый или
  Control-клик открывает меню;
- тултип иконки — `NSStatusItem.button.toolTip = "SnapBrief"`;
- всплывающая подсказка заменяется системным уведомлением (§9.9);
- галочка пункта — `NSMenuItem.state = .on`;
- разделитель — `NSMenuItem.separator()`.

Приложение работает как agent: `LSUIElement = true`, нет иконки в Dock, нет стандартного главного
меню. Пункт «Выйти» вызывает `NSApp.terminate(nil)` после принудительного сохранения сессии
и **отменяет выход**, если сохранение не удалось, как на Windows (`:764-772`) — через
`applicationShouldTerminate` с возвратом `.terminateCancel`.

### 9.8 Окна: поверх всего, без активации, без захвата

| Задача | Windows | macOS |
|---|---|---|
| Оверлей поверх всего | `Topmost` плюс `SetWindowPos(HWND_TOPMOST)` | `NSWindow.level = .screenSaver`; `collectionBehavior` включает `.canJoinAllSpaces` и `.fullScreenAuxiliary` |
| Стопка поверх без фиксации | `SetWindowPos(HWND_TOP, SWP_NOACTIVATE)` | `orderFront(nil)` вместо `makeKeyAndOrderFront`; уровень `.floating` **не** ставить |
| Показ без активации | `ShowActivated = false` | подкласс `NSWindow` с `canBecomeKey = false` для стопки, либо `orderFrontRegardless()` |
| Не в панели задач | `ShowInTaskbar = false` | автоматически при `LSUIElement` |
| Исключение из чужих захватов | `SetWindowDisplayAffinity(WDA_EXCLUDEFROMCAPTURE)` | `NSWindow.sharingType = .none` |
| Скрыть свои окна перед кадром | скрытие плюс прокачка отрисовки плюс `DwmFlush()` | исключить свои окна из `SCContentFilter` — **предпочтительно**, точнее и быстрее; либо `orderOut(nil)` плюс `CATransaction.flush()` плюс ожидание кадра |
| Перетаскивание за заголовок | `DragMove()` | `isMovableByWindowBackground` либо ручная обработка перетаскивания |
| Окно без системной рамки | `WindowStyle = None` | `styleMask = [.borderless]`, прозрачный фон, `isOpaque = false` |

**Важно про полноэкранный оверлей.** Windows-версия делает окно **непрозрачным** и рисует в нём
замороженный рабочий стол (§1.2, `tasks/verification.md:67`). На macOS повторить ровно это:
непрозрачное окно с картинкой, а не прозрачный слой с реальным рабочим столом под ним.
Иначе появятся те же проблемы с производительностью и с перехватом кликов, ради решения которых
Windows-версия и отказалась от per-pixel прозрачности.

### 9.9 Уведомления

Windows: всплывающая подсказка трея на 2000 мс, без разрешений.
macOS: `UNUserNotificationCenter`, требуется разрешение, время показа управляется системой.

**Решение.** Запрашивать разрешение **лениво**, при первом уведомлении, а не при старте.
При отказе уведомления не показывать и **не** показывать ошибку: настройка «Уведомления о
копировании и сохранении» остаётся включённой, но фактически не работает. Это допустимо,
поскольку уведомление вторично. Альтернатива без разрешений — кратковременно менять иконку
в menu bar, но это расхождение с Windows, вводить его без просьбы пользователя не надо.

### 9.10 Диалоги файлов и sandbox

| Windows | macOS |
|---|---|
| диалог сохранения с фильтром и предупреждением о перезаписи | `NSSavePanel`, `allowedContentTypes = [.png, .jpeg]`, предупреждение встроено |
| диалог открытия с множественным выбором | `NSOpenPanel`, `allowsMultipleSelection = true`, `allowedContentTypes = [.png, .jpeg]` |
| диалог выбора папки | `NSOpenPanel` с `canChooseDirectories = true`, `canChooseFiles = false` |

Расхождение: на macOS переключение типа файла в панели **меняет расширение автоматически**,
поэтому проверка «расширение не PNG и не JPEG» (§1.13, шаг 5) практически недостижима,
но её надо сохранить как защиту.

Если приложение пойдёт в App Store и будет работать в sandbox, доступ к пользовательской папке
сохранения потребует **security-scoped bookmark**: в настройках хранить не путь, а закладку,
и открывать доступ через `startAccessingSecurityScopedResource`.
Вне sandbox (прямое распространение с notarization) достаточно обычного пути, как на Windows.
**Рекомендация: sandbox не использовать** — приложение по своей природе требует Screen Recording,
Accessibility и записи по произвольным путям, и App Store всё равно не примет его без переработки.

### 9.11 Атомарная запись и файловая система

| Windows | macOS |
|---|---|
| временный файл плюс перемещение с перезаписью | `FileManager.replaceItemAt` либо `Data.write(to:options: .atomic)` |
| сквозная запись `WriteThrough` | `F_FULLFSYNC` через `fcntl`, если нужна гарантия |
| регистронезависимые сравнения путей | APFS по умолчанию регистронезависима, но может быть чувствительной; сравнивать через `standardizedFileURL` и `resolvingSymlinksInPath` |
| проверка «путь внутри каталога» по префиксу строки | то же, но по стандартизованным URL, не по строкам |

Проверка выхода за пределы каталога сессии (§4.4, §2.5) обязательна и должна учитывать симлинки.

### 9.12 Шрифты

`Segoe UI` и `Segoe UI Variable Text` на macOS отсутствуют. Замена — системный шрифт
`NSFont.systemFont(ofSize:weight:)`. Соответствие начертаний: Normal — `.regular`,
SemiBold — `.semibold`, Bold — `.bold`. Кегли сохраняются числом.

**Следствие:** экспортные PNG **не будут попиксельно идентичны** Windows-версии там, где есть
текст: шапка, круглые подписи, текстовые отметки. Это неизбежно. Тесты, сравнивающие пиксели,
должны проверять текстовые области по признаку «есть светлые пиксели» (как уже делает smoke,
§8.4 пункт 12), а не по точному совпадению.

### 9.13 Сборка и распространение

Windows: self-contained x64, один исполняемый файл, ярлык на рабочем столе, запуск без
установленного .NET.
macOS: `.app`-бандл, universal (arm64 и x86_64), **обязательны подпись Developer ID и
notarization**. Иначе Gatekeeper заблокирует запуск, а TCC-разрешения будут сбрасываться при
каждом изменении бандла — это отдельная практическая боль при разработке: неподписанные
пересборки заставляют заново выдавать Screen Recording.

Минимальная версия — **macOS 14.0**: обусловлена `SCScreenshotManager` (14.0) и общей политикой
ScreenCaptureKit. Если понадобится 13.x, захват придётся делать через `SCStream` с одним кадром.

`Info.plist` обязан содержать `LSUIElement = true` и `NSHighResolutionCapable = true`.
Строки usage-description для Screen Recording, Accessibility и Input Monitoring не требуются
(они управляются TCC без них), но объяснение назначения разрешений **должно быть в интерфейсе**.

## 10. Открытые вопросы

Только то, что действительно нельзя решить из Windows-кода. Всё остальное в спеке определено.

### Блокеры (нужен ответ до начала соответствующей части)

**Q1. Дефолтная горячая клавиша быстрого сохранения экрана.**
На Windows это Shift+Print Screen. На macOS клавиши Print Screen нет, а `Shift+Cmd+3`,
`Shift+Cmd+4` и `Shift+Cmd+5` заняты системными снимками. Предложение спеки —
`Shift+Cmd+Option+S`, выключено по умолчанию. Нужно подтверждение либо другое сочетание.
*Влияет на:* §1.14, §7.6. Не блокирует остальную работу, потому что функция выключена по умолчанию.

**Q2. Идентификация целевых приложений на macOS.**
Windows-профили (§5.3) опознают получателей по имени процесса: `ChatGPT`, `Claude`, `Code`,
`WindowsTerminal`. На macOS нужны **bundle identifier** установленных приложений Никиты.
Из кода их получить невозможно. Нужен список фактических значений для: Codex/ChatGPT desktop,
Claude desktop, Terminal или iTerm2, VS Code.
*Влияет на:* §5.3, §5.4. Без ответа Codex-догон текста нельзя реализовать корректно.

**Q3. Совместный приём нескольких изображений и текста на macOS.**
Это **не решённый вопрос и на Windows**: `tasks/verification.md:3` прямо говорит, что совместный
приём всеми четырьмя получателями ещё не подтверждён, а `tasks/verification.md:17` фиксирует
наблюдение, что Codex Desktop приложил изображение, но не текст.
На macOS набор форматов другой (§9.14, строка 10), поэтому результат может отличаться в любую
сторону. Требуется тот же практический эксперимент: три различимых PNG (A, B, C), русские заметки,
пустой черновик, 10 повторений, фиксация версий приложений.
*Влияет на:* §1.10, §5. **Реализацию не блокирует** — основной сценарий (положить пакет в буфер,
пользователь вставляет сам) работает независимо от результата. Блокирует **заявление о готовности**.

### Требуют решения, но не блокируют старт

**Q4. Многоэкранный захват со смешанным масштабом.**
§9.5 предлагает два варианта: собирать общий кадр в пикселях максимального масштаба либо снимать
только тот дисплей, где идёт выделение. Windows-версия работает с одним прямоугольником, потому что
драйвер отдаёт согласованные пиксели; на macOS такого нет. Выбор нужно сделать и **проверить
на реальной конфигурации Никиты** — из кода это не выводится.
Замечу: `tasks/verification.md:48` фиксирует, что и на Windows «края, отрицательный origin и
смешанный DPI на целевой конфигурации не проверены».

**Q5. Sandbox и способ распространения.**
§9.10 рекомендует не использовать sandbox и распространять напрямую с Developer ID и notarization.
Если нужен App Store, меняется работа с папкой сохранения (security-scoped bookmarks) и,
скорее всего, приложение вообще не пройдёт review из-за Accessibility и Input Monitoring.
Нужно подтверждение способа распространения.

**Q6. Локализация диагностических сообщений.**
На Windows строки статуса и ошибок (§1.20) **не переведены** и остаются русскими даже при
английском интерфейсе (`tasks/verification.md:110`). Порт может воспроизвести это 1:1 либо
локализовать полностью. Спека допускает второе как улучшение. Нужно решение, чтобы не спорить
на ревью.

**Q7. Одиночный модификатор как глобальная горячая клавиша.**
Windows-версия это позволяет (§7.3, запись на отпускании чистого модификатора).
На macOS через Carbon это невозможно, только через event tap с Input Monitoring (§7.6).
Варианты: убрать возможность, оставить с оговоркой о разрешении, либо переключить всю регистрацию
горячих клавиш на event tap. Спека рекомендует средний вариант; нужно подтверждение.

### Явно НЕ вопросы (решено в спеке, не переоткрывать)

- Разделитель пути в `sourceImagePath` — прямой слэш при записи, оба принимаются при чтении (§3.7).
- Алгоритм размытия — трёхпроходный box-blur, **не** `CIGaussianBlur` (§2.8).
- Каталог данных — `~/Library/Application Support/SnapBrief/` (§3.7).
- `MainWindow` не портируется (§6.6).
- Строка выбора получателя в стопке не портируется как видимый UI (§1.9).
- Общего комментария ко всей стопке нет; поле `globalNote` только для совместимости данных (§1.4).
- Enter никогда не инжектируется (§5.6), но может быть назначен горячей клавишей (§7.3).
