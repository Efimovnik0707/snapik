## Автоматические проверки

- Размытие изменяет только целевую область, сохраняет размер/DPI и исходник; непрозрачное скрытие применяется после прочих правок.
- Обрезка сохраняет отдельные видимые сегменты линий без ложных соединений, ID и заметки; загрузка старых сессий schema 1 совместима.
- Smoke вызывает реальную кнопку заметки, проверяет связь текста и метки A1 с экспортом, сохранение прежних файлов и восстановление новой пустой сессии после перезапуска. Это не проверка физического фокуса Windows.
- Clipboard одного снимка содержит PNG/DIB/Bitmap, files и text. Несколько снимков сохраняют полный ordered files/text пакет без ложной выдачи только первого bitmap.
- Транспорт проверяет смену фокуса/clipboard, отмену, повторные и синтетические клавиши; изменение буфера или фокуса во время отпускания клавиш блокирует дополнительную вставку.

Шесть новых geometry-тестов проверяют все углы, сохранение противоположного угла, ограничения и преобразование координат. Расширенный WPF smoke выполняет сужение, Undo, Redo и расширение на синтетических снимках со стрелкой и privacy-аннотациями; проверяет размер, позицию, ID и заметку. Pipeline и экспорт прошли. ## Многоразовый пакет, 9 сентября

Причина по `startup.log` пользователя (строки `PasteIntent …`): после успешной поштучной вставки в Claude Desktop (`CompletedUnverified`) `CompletePasteIntentAsync` сразу вызывал `StartNewSessionAsync`, который обнулял `_ownedClipboardReceipt`/`_ownedClipboardPromptText`/`_prepared` и очищал стопку; в системном буфере после этого оставался только текст последнего шага последовательности (`SetTextGuardedAsync`), не составной пакет. Следующие Ctrl+V/Alt+V в терминале и других окнах приходили в предикат перехвата с `ownedSeq=пусто, prepared=False` и не перехватывались — вставлялся только текст.

Изменение: `CompletePasteIntentAsync` (оба пути, перехваченный `CompleteSequentialAsync` и Codex-путь `CompleteAsync`) при `CompletedUnverified` больше не начинает новую сессию сразу, а вызывает новый `RepublishPackageForReuseAsync` внутри той же критической секции `_clipboardPublicationGate` (гейт освобождается только в `finally` вызывающего метода). Тот же пакет (пути и текст, снятые в `OnPasteIntentObserved` до релиза клавиатурного хука) публикуется заново через `SetPackageGuardedAsync` с ожидаемым sequence, равным receipt только что завершённого шага; `_ownedClipboardReceipt` и `_ownedClipboardPromptText` обновляются, `_prepared` не трогается, взводится новый флаг `_pasteObservedForCurrentPackage`. Статус стопки — новая пара RU/EN в `UiLanguage.cs`: «Вставлено: {0} изображений · {1} заметок. Пакет остаётся в буфере, следующий снимок начнёт новую стопку». Если между завершением вставки и republish кто-то другой уже заменил буфер, `SetPackageGuardedAsync` бросает `ClipboardChangedException`: republish не выполняется, владение буфером сбрасывается (`_ownedClipboardReceipt = null`), статус — «Пакет вытеснен другим приложением. Сессия сохранена.» (новая пара в `UiLanguage.cs`), чужой буфер не перезаписывается.

Ротация сессии перенесена на начало следующего захвата: `EnsureCurrentCaptureSessionAsync` в самом начале проверяет `_pasteObservedForCurrentPackage`; если флаг взведён — сбрасывает его, обнуляет `_ownedClipboardReceipt`/`_ownedClipboardPromptText` и вызывает `StartNewSessionAsync` (старая сессия уже сохранена на диске SaveAsync внутри StartNewSessionAsync), не проверяя при этом «чужой буфер» отдельно — сама ротация ничего не читает из текущего системного буфера и его не трогает. Существующая проверка «буфер заменён другим приложением → новая сессия» (`_ownedClipboardReceipt is { } receipt && IsCurrentAsync(...)`) осталась ниже по коду без изменений и продолжает работать для случая, когда флаг не взведён (обычный захват без промежуточной вставки).

Решение по пункту плана про импорт/восстановление снимка после вставки: флаг `_pasteObservedForCurrentPackage` **не сбрасывается** операциями `ImportFileAsync`, `ImportClipboardAsync` и `RestoreRemoved` — они не вызывают `EnsureCurrentCaptureSessionAsync`, поэтому продолжают дополнять ту же (уже вставленную) стопку как раньше. Единственное место, где флаг проверяется и потребляется — начало следующего реального захвата (`CaptureLoopAsync` → `EnsureCurrentCaptureSessionAsync`). Практически это эквивалентно варианту «как при новом снимке»: если пользователь дополнил стопку импортом/восстановлением после вставки, а затем сделал новый снимок, старая сессия (включая добавленный/восстановленный элемент) уходит в архив на диске как единое целое, а новая стопка стартует пустой — ничего не теряется, просто дополненная стопка становится частью сохранённой «старой» сессии. Выбран этот вариант, а не немедленный republish буфера при импорте/восстановлении, чтобы не добавлять скрытую публикацию буфера в путь, который сейчас не трогает буфер вовсе.

Тесты: `tests/SnapBrief.Windows.Tests/CodexDesktopPasteCompletionServiceTests.cs` — `FakeClipboard.SetPackageGuardedAsync` реализован (было `NotSupportedException`) и пишет маркер `PACKAGE:<paths>` + `WrittenText`. Новый `ReusablePackage_RepublishesFullPackageAfterCompletedPasteAndAcceptsNextIntent` прогоняет `CompleteSequentialAsync` до `CompletedUnverified`, затем republish-вызов `SetPackageGuardedAsync` с sequence завершённого шага и проверяет: буфер снова содержит оба файла и текст под новым sequence, `IsCurrentAsync` подтверждает владение, а второй `PasteIntentObserved` с этим новым sequence снова успешно проходит `CompleteSequentialAsync` (эквивалент повторного перехвата предиката в `EdgeStackWindow`, чьи sequence-проверки идентичны). Новый `ReusablePackage_DisplacedByAnotherAppLeavesClipboardUntouched` проверяет, что внешняя запись в буфер между завершением и republish (`ExternalWrite`) приводит к `ClipboardChangedException` при попытке republish — это ветка `RepublishPackageForReuseAsync` в `EdgeStackWindow`, не перезаписывающая чужой буфер. Предикат перехвата в `EdgeStackWindow` (замыкание в конструкторе) и `EnsureCurrentCaptureSessionAsync` остаются непокрыты юнит-тестами, как и раньше — они не были покрыты ни до этой правки (в проекте нет способа собрать `EdgeStackWindow` в тестовом хосте без WPF Application, `SmokeTestRunner` тоже не создаёт это окно, а работает только с `SessionWorkspace`); это существующее ограничение, а не новый пробел.

Проверка: полный `scripts/build.ps1` прошёл — 85 тестов (14 imaging, 18 core, 53 transport) и WPF smoke. Публикация запущена. Живьём не проверено (открыто на пользователя): последовательная вставка одного и того же пакета в Claude Desktop, затем в терминал/другое приложение без нового снимка между ними, статус «Пакет остаётся в буфере…», и что новый снимок после такой серии действительно стартует новую стопку, сохраняя предыдущую на диске. Формат `session.json`/`manifest.json`/`settings.json` не менялся.

## Отзвук буфера от получателя, 9 сентября

Факт от пользователя: после поштучной вставки пакета в Claude Code внутри терминала VS Code сам терминал перезаписывает буфер обмена текстом того, что вставилось — например `[Image #2]Снимок A.\r\n  A1: тест1` (`[Image #N]` — плейсхолдер картинки в интерфейсе Claude Code). В `startup.log` это видно как скачок sequence на ~17 сразу после нашей ре-публикации через `RepublishPackageForReuseAsync`. Следующее Ctrl+V в другом приложении (наблюдался GrokBot) попадает в предикат перехвата с `ownedSeq != intentSeq` (наш `_ownedClipboardReceipt` всё ещё указывает на старый sequence нашего пакета, а буфер уже содержит чужой sequence от отзвука терминала) → предикат возвращает `false`, Ctrl+V не перехватывается → в GrokBot вставляется этот чужой текст вместо нового Ctrl+V нашего пакета. Вставка Claude Desktop → GrokBot (без терминала между ними) работает, потому что Claude Desktop не пишет такой отзвук.

**Механизм.** Новый статический класс `ClipboardEchoDetector.IsReceiverEcho(ClipboardSnapshot snapshot, string promptText)` в `src/SnapBrief.Windows/ClipboardEchoDetector.cs` (без WPF-зависимостей) классифицирует расхождение sequence: отзвук — если в снапшоте нет ключа `FileDrop`, нет ни одного из `Bitmap`/`DeviceIndependentBitmap`/`PNG`, есть текст под `UnicodeText` или `Text`, и этот текст после нормализации (`[Image #N]` вырезан по regex, пробелы/переводы строк схлопнуты, `Trim`) равен нормализованному prompt-тексту пакета или содержит его как подстроку. `EdgeStackWindow` в `src/SnapBrief.App/EdgeStackWindow.xaml.cs`: после каждой успешной ре-публикации в `RepublishPackageForReuseAsync` запускается фоновый наблюдатель `WatchForReceiverEchoAsync` (один активный на пакет, через `_receiverEchoWatchCts`), опрашивающий `_clipboard.CaptureAsync` каждые 200 мс (`ReceiverEchoPollInterval`) в течение окна `ReceiverEchoWatchWindow` = 6 с (константа, окно продлевается на новые 6 с при каждом обнаруженном отзвуке). При расхождении sequence: если снапшот классифицирован как отзвук — наблюдатель берёт `_clipboardPublicationGate`, повторно публикует тот же пакет через `SetPackageGuardedAsync` с `expectedSequence`, равным sequence отзвука, обновляет `_ownedClipboardReceipt`/`_ownedClipboardPromptText`, пишет в журнал `PasteIntent re-armed after receiver echo: from seq X to Y`; если это чужое копирование — наблюдение останавливается без публикации, журнал `PasteIntent package displaced by foreign clipboard write`. Наблюдатель отменяется (`CancelReceiverEchoWatch`) при новом захвате/новой сессии (`StartNewSessionAsync`), новой явной публикации пакета (`SaveAndCopyCommittedPackageAsync`, `CopyPackageAsync`, `RefreshOwnedClipboardAsync` — переупорядочивание/удаление/восстановление снимка), закрытии окна (`OnClosing`) и при вытеснении буфера сторонним приложением, обнаруженном самим наблюдателем или первичным `RepublishPackageForReuseAsync`. Предикат перехвата и `OnPasteIntentObserved` не менялись: они читают тот же `_ownedClipboardReceipt`, который наблюдатель держит актуальным, поэтому повторное Ctrl+V/Alt+V после re-arm снова проходит без изменения логики хука.

**Что проверено.** Полный `scripts/build.ps1` прошёл — 90 тестов (14 imaging, 18 core, 58 transport) и WPF smoke; новые 5 тестов `tests/SnapBrief.Windows.Tests/ClipboardEchoDetectorTests.cs` — отзвук с `[Image #2]` и CRLF/пробелами (оба распознаны как отзвук), чужой текст без совпадения с prompt, чужой текст при наличии `FileDrop` (не отзвук даже при совпадении текста), буфер с `Bitmap`-форматом (не отзвук, даже если текст совпадает с prompt — считается конкурирующей вставкой изображения, а не эхом терминала). Все 480 файлов публикации сверены по SHA-256 (EXE `0b43c0f27f960141966399c8eecef2a4a771b1f76aea11cbaceff07f6142846` (SHA-256)), приложение перезапущено.

**Что живьём не проверено (открыто на пользователя).** Повторная вставка того же пакета в терминал с Claude Code сразу после первой (ожидаемый лог `re-armed after receiver echo`), затем успешное Ctrl+V в GrokBot тем же пакетом без нового снимка между ними; поведение, если отзвук терминала приходит позже 6 секунд (в этом случае `ReceiverEchoWatchWindow` стоит увеличить, но фактическая задержка отзвука в `startup.log` пользователя ещё не измерена); поведение при нескольких последовательных отзвуках подряд (продление окна на каждый); отсутствие ложных срабатываний, когда пользователь сам скопировал текст, случайно похожий на prompt пакета, сразу после вставки.

## Настройки сливаются при записи, импорт и статусы, 12 сентября

Два писателя одного `settings.json` (панель и редактор) перестали затирать друг друга. `HotkeySettings.TryLoad(path, out settings)` (`HotkeySettingsWindow.xaml.cs`) различает «файла нет» (вернуть дефолты, писать можно) и «файл есть, но не читается» (`false`, писать нельзя); `Load` теперь обёртка над ним, формат файла не менялся. `SaveAppearanceDefaults` в редакторе при нечитаемом файле просто не пишет, а не сохраняет дефолты поверх всех настроек. Мелкое в том же коммите: `SessionWorkspace.LoadBitmap` отдаёт «Формат не поддерживается системой» и когда падает уже получение кадра или в файле нет кадров; окно просмотра снимка открывается под `SuspendTopmost()`; `SuspendTopmost` считает вложенность и возвращает `Topmost` только при обнулении счётчика; «Не удалось сохранить настройки» и статусы «Снимок удалён», «Снимок восстановлен.», «Порядок снимков изменён.», «Пакет сохранён.», «Готово: {0} изображений · {1} заметок» переведены на пары в `UiLanguage`, а сами статусы — на `ShowTransientStatus` (обычный `SetStatus` показывает только ошибки, то есть раньше они были не видны); `_statusTimer` останавливается в `OnClosing` рядом с `_saveTimer`; крестик в заголовке панели получил `Stretch="Uniform"` (обводка вылезала за 10×10, тот же дефект, что у иконки нового снимка); `EdgeStackWindow.xaml.cs` пересохранён без UTF-8 BOM, содержимое не менялось.

Удаление снимка показывает «Снимок удалён · Отменить» / "Capture removed · Undo"; «Отменить» вызывает тот же `RestoreRemoved()`, что и пункт меню «•••» → «Вернуть удалённый снимок» (он остаётся как долгий путь), снимок возвращается на прежний индекс из стека `_removed`. Новых пар в `UiLanguage` не потребовалось: «Снимок удалён» и «Отменить» уже в таблице.

Двух механизмов подсказок не осталось: `ShowTransientStatus` и `_statusTimer` удалены, все их вызовы (импорт файла, вставка из буфера, «Пакет сохранён.», «Готово: {0} изображений · {1} заметок», порядок снимков, восстановление снимка) переведены на `ShowToast` без действия. `SetStatus(text, error: true)` по-прежнему пишет ошибку в `StatusText` и живёт до следующего статуса.

Проверка: тесты Release (90) и WPF smoke прошли. Живьём не проверено: сам fade и то, что тост не перекрывает статус ошибки при одновременном показе.

## Вставленные снимки остаются в ленте, 12 сентября

**Изменение формата.** В `session.json` у снимка появился `captures[].sent` (bool, по умолчанию `false`), в `settings.json` — `ClearStackAfterPaste` (bool, по умолчанию `false`). Оба аддитивные: старый файл без ключа читается и даёт `false`, новый файл читается старым билдом (лишние ключи игнорируются). Mac переносит поле, ключ и дефолты синхронно.

Ротация сессии после вставки убрана. Замеченная вставка (`CompletePasteIntentAsync`, обе ветки: `CompletedUnverified` после `RepublishPackageForReuseAsync` и `NotApplicable` при физическом Ctrl+V в Codex Desktop) помечает снимки как отправленные по Id из `_prepared.Manifest.Images[].CaptureId`, снятым в момент интента рядом с `pathsAtIntent`, а не по индексу: лента могла измениться, пока завершалась вставка. Флаг `_pasteObservedForCurrentPackage` и отложенная ротация удалены, ветка «чужое копирование в буфер» в `EnsureCurrentCaptureSessionAsync` тоже: сам метод после этого выродился и удалён вместе с вызовом из `CaptureLoopAsync`. Поле `_sessionResetting` осталось — оно по-прежнему защищает предикат перехвата и повторный вход, пока идёт очистка ленты.

В пакет для буфера идут только неотправленные снимки (`SaveAndCopyCommittedPackageAsync`, `RefreshOwnedClipboardCoreAsync`). Если неотправленных нет, пакет в буфер не кладётся: `_prepared`, receipt и текст сбрасываются, поэтому предикат перехвата не срабатывает на чужой буфер. Явные «Копировать пакет» и «Сохранить пакет…» по-прежнему берут всю ленту (ручное действие). `SessionWorkspace.PrepareAsync` получил перегрузку с отдельным списком снимков пакета: в `session.json` пишется вся лента, а экспортируется только её неотправленная часть, иначе фильтр стирал бы отправленные снимки с диска.

Чистые правила вынесены в `SnapBrief.Core.Exporting.SentCaptureRules`: `ForPackage` (что идёт в пакет) и `StripLabels` (буквы неотправленным с A, `null` отправленным). `Renumber` раздаёт буквы по `StripLabels`, отправленный снимок сохраняет ту букву, с которой ушёл, а на карточке вместо буквы показывается галочка (`DataTrigger` по `IsSent`: `Opacity 0.45`, приглушённая рамка и бейдж). Счётчик в шапке и активность кнопки вставки считаются по неотправленным; новый снимок и открытие редактора получают номер тоже по неотправленным, чтобы бейдж в панели, шапка редактора и `prompt.md` показывали одну букву. Правка снимка снимает флаг: после разметки в ленту кладётся новый объект, а `PersistPreviewChangesAsync` явно ставит `IsSent = false`.

«Новая сессия» в меню «•••» заменена на «Очистить ленту» / Clear the strip, рядом с «•••» в шапке появилась иконка корзины с тем же действием. Очистка — прежняя `StartNewSessionAsync` без `HideStack()`: сессия архивируется на диске, открывается пустая, панель остаётся видимой, тост «Лента очищена» / Strip cleared. Подтверждения и отмены нет, файлы прошлой сессии остаются на диске. Настройка «Очищать ленту после вставки» / Clear the strip after pasting (вкладка «Общие») переключает точку пометки на очистку.

Побочный эффект в том же коммите: `SessionWorkspace.PrepareAsync` после успешной подготовки оставляет в `exports/` только три последних каталога `revision-*` (имя с `D6`-номером ревизии сортируется как номер), каталог текущего пакета не удаляется никогда, а каталог, который держит другой процесс, оставляется до следующего запуска. Без этого лента, живущая через вставки, копила бы полный экспорт на каждый снимок.

Проверка: тесты Release (92) и WPF smoke прошли. Новые Core-тесты: round-trip `sent = true` через `JsonSessionStore` и чтение файла без поля как `false`; `SentCaptureRules` на ленте из четырёх снимков (пакет только из неотправленных, метки `null, A, null, B`). Транспортные тесты не менялись и проходят как есть. Smoke: снимок помечается отправленным, переживает перезапуск воркспейса, пакет собирается из двух оставшихся с метками A и B, в `prompt.md` нет «Снимок C», каталогов `revision-*` не больше трёх, каталог текущего пакета на месте; `ClearStackAfterPaste` добавлен в round-trip настроек. Живьём не проверено: три снимка → Ctrl+V в Claude Code → лента затемнена с галочками и счётчиком 0 → четвёртый снимок получает букву A и уходит один; включённая настройка «Очищать ленту после вставки».

## Текст пакета только у снимков с заметками, 12 сентября

**Изменение формата.** `prompt.md` теперь не пишется, когда текст пакета пуст, и в `manifest.json` у такого пакета `promptFileName` и `promptSha256` — пустые строки, `promptText` пустой. Схема полей не менялась, но читатель манифеста должен допускать пустое имя файла. Mac зеркалит `PromptGenerator` и это поведение `FileExportService`.

Секция «Снимок X.» попадает в текст только если у снимка есть заголовок, комментарий к снимку или хотя бы одна заметка на отметке (`PromptGenerator`). Снимок без заметок больше не даёт строку «Снимок A.» рядом с картинкой; если таких снимков нет вовсе и общее пожелание пусто, текст пакета пустой. Буквы по-прежнему берутся из позиции снимка в переданном списке, поэтому бейджи в панели, подпись в экспортном PNG и метки в тексте совпадают.

Пустой текст перестал быть ошибкой в транспорте, четыре точки: предикат перехвата (`EdgeStackWindow.xaml.cs`) требует `_ownedClipboardPromptText is not null` вместо непустой строки; `CodexDesktopPasteCompletionService.CompleteAsync` при пустом тексте не возвращает `NothingToDispatch`, а сразу отдаёт `CompletedUnverified` (картинки уже вставил сам пользователь, второго шага нет), `CompleteSequentialAsync` шлёт картинки и завершается тем же статусом с последним receipt картинки; `WindowsClipboardService.CreatePackageDataObject` не добавляет `UnicodeText` при пустом тексте, иначе в текстовое поле получателя вставлялась бы пустая строка; `StartReceiverEchoWatch` при пустом тексте не запускается, потому что эха такого текста не бывает. `NothingToDispatch` остался только для пакета без картинок. В `PasteCoordinator` проверка «Текст задания пуст» убрана из `ValidatePackage`, шаг текста в staged-пути выполняется только при непустом тексте, `verified` считается по картинкам, а восстановление буфера пропускается, если ни одной записи в буфер не было. «Сохранить пакет…» копирует файлы каталога пакета как есть, поэтому без `prompt.md` в папку попадают только изображения и манифест.

Проверка: тесты Release (96) и WPF smoke прошли. Новые Core-тесты: снимок без заметок не даёт секции, а вторая картинка с заметкой даёт «Снимок B» без «Снимок A»; сессия без заметок даёт пустую строку, общее пожелание при этом остаётся; пакет без заметок не пишет `prompt.md` и оставляет пустые `promptFileName`/`promptSha256`. Транспортные тесты: `CompleteAsync` с пустым текстом даёт `CompletedUnverified` без записей в буфер и без нажатий, перехваченная вставка пакета без текста шлёт только картинки, staged-вставка без текста завершает `CompletedVerified` с двумя нажатиями и `TextDispatched = false`. Существующие кейсы с текстом не менялись. Живьём не проверено: один снимок без заметок → Ctrl+V в Claude Code даёт только картинку, и то же в обычном текстовом поле не вставляет пустую строку.
