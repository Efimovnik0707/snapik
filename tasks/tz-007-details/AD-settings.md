## A1. Окно настроек режет низ вкладки «Вид»

### Причина

Окно жёсткое: `Width="620" Height="520" ResizeMode="NoResize"` (`src/Snapik.App/HotkeySettingsWindow.xaml:3`). Внутри `Border` с `Padding="24"` и рамкой 1 px (`:10`), четырёхрядная сетка (`:12`), где ряд 1 это `TabControl` с `Height="*"` (`:19`). Вкладка «Вид» (`:65-67`) показывает `AppearancePicker` с `ShowPaletteRow="True"`, то есть все пять блоков контрола: галерея тем, ряд акцентов, блок палитр и образец (`Controls/AppearancePicker.xaml:81-126`). Ряд `*` не умеет ужимать `StackPanel` внутри себя: содержимое просто выходит за клип окна, и низ образца (`:113-125`) уезжает под нижний край. Скролла в окне нет нигде.

Разбивка по 364 px вкладки «Вид» (ручной расчёт, не замер):

| Блок | Строки | px |
|---|---|---|
| Подпись «Тема · фон и панели» + отступ | `AppearancePicker.xaml:82` | 24 |
| Галерея тем (карточка 64 превью + 16 подпись + 6 + padding 12 + рамка 4) + отступ 22 | `:83-97` | 124 |
| Подпись «Цвет …» + отступ | `:99` | 24 |
| Ряд акцентов (точки 28) + отступ 18 | `:100` | 46 |
| Блок палитр (подпись 24 + сегменты 26) + отступ 18 | `:104-111` | 68 |
| Образец (содержимое 34 + padding 24 + рамка 2) | `:113-125` | 60 |
| `Margin="0,10,0,0"` вкладки + дефолтный `Padding` `TabControl` | `HotkeySettingsWindow.xaml:65`, `:19` | 18 |

Плюс вне вкладки: шапка с отступом 50 (`:13-18`), ряд вкладок около 46 (`TabItem` `Padding="15,9" Margin="0,0,6,12"`, `:8`), ряд кнопок 50 (`:70-73`, `BaseButton` `MinHeight="34"`, `Themes/SnapikTheme.xaml:24`), рамка и padding 50 (`:10`). Итого около 560 против 520.

Почему у мастера то же самое влезает: окно 600 (`OnboardingWindow.xaml:3`), блок палитр там скрыт (п. 4 раздела 0), и над всем стоит `ScrollViewer` с `MaxHeight` от рабочей области монитора (`OnboardingWindow.xaml.cs:148`).

### Варианты решения

1. **`Height="620"`, как предлагает ТЗ.** Одна правка, ноль риска для разметки, 60 px запаса сверх расчётных 560. На 125 % это 775 физических px, полезная высота монитора 1080@125 % равна 824 DIP по уже существующей и проверенной арифметике `OnboardingWindow.UsefulHeight` (`SmokeTestRunner.cs:1240`), то есть влезает с запасом. Минус: следующая добавленная строка в любой вкладке обрежется так же молча.
2. **`SizeToContent="Height"`.** Окно начнёт прыгать при переключении вкладок, ТЗ это прямо запрещает. Отпадает.
3. **Высота по самой высокой вкладке, посчитанная в коде.** `TabControl` реализует только выбранную `TabItem`, поэтому «самую высокую» надо строить руками (создавать содержимое всех четырёх вкладок вне дерева и мерить). Это заметный кусок кода ради числа, которое меняется раз в полгода. Отпадает по соотношению цены и пользы.
4. **`ScrollViewer` вокруг содержимого вкладок.** Решает проблему навсегда и на любом масштабе, но меняет вид окна (полоса прокрутки в настройках выглядит как «не поместилось») и спорит с ощущением диалога фиксированного размера. В этот раунд не предлагаю.

**Рекомендую вариант 1 плюс проверку, которая меряет по-настоящему** (см. «Тесты»). Число в XAML остаётся простым, а от повторения защищает тест, а не человеческая внимательность.

## D1. Громкость: квадратичная шкала, тик при отпускании, подпись «60 %»

### Причина

Шкала линейная. `UiSoundService.Sound.Play` (`src/Snapik.App/UiSoundService.cs:90-101`) ставит `player.Volume = Math.Clamp(volume, 0, 100) / 100.0 * gain` (`:96`), где `gain` это 0.6 у затвора, 0.25 у тика, 0.7 у «скопировано» (`:22-24`). `MediaPlayer.Volume` это линейная амплитуда, поэтому 100 → 50 даёт ровно −6 дБ, 50 → 25 ещё −6, и верхняя половина хода ползунка на слух почти неразличима. Значение приходит из настроек: ползунок 0..100 (`HotkeySettingsWindow.xaml:32`), читается в `:48`, пишется в `:236`, попадает в файл через слияние `EdgeStackWindow.xaml.cs:1449`.

Тика при регулировке нет вовсе: `VolumeSlider` в XAML не имеет ни одного обработчика (`HotkeySettingsWindow.xaml:32`), в код-бихайнде к нему привязано только чтение при открытии и запись при сохранении. Пользователь крутит вслепую.

Числа рядом с ползунком нет: подпись это статический `TextBlock Text="Громкость"` (`:31`).

### Варианты решения

**Кривая.**
1. Квадрат `(v/100)² × gain`, как в ТЗ. 100 → без изменений, 50 → −12 дБ, 25 → −24 дБ, 0 → тишина. Просто, обратимо, ничего не хранит.
2. Настоящая перцептивная кривая (например `10^((v−100)·0.03)`, то есть −60 дБ на нуле). Точнее по слуху, но требует отдельного разбора «что считать нулём», и на нуле надо всё равно вручную глушить в 0. Избыточно для задачи.

Рекомендую 1, как в ТЗ.

**Где живёт формула.** Не внутри `UiSoundService`, а отдельным файлом (п. 8 раздела 0), иначе её нельзя покрыть юнит-тестом.

**Момент тика.** Один `DispatcherTimer` на 150 мс, перезапуск на каждом `ValueChanged` (п. 6 раздела 0). `Thumb.DragCompleted` не добавляю: второй вход в ту же функцию это второй шанс получить двойной тик, а разница в 150 мс на слух не проблема.

**Подпись.** Отдельный маленький `TextBlock` справа от ползунка, `Foreground="{DynamicResource TextMutedBrush}"`, `FontSize="12"`, текст `$"{(int)VolumeSlider.Value} %"` (с пробелом перед `%`, как в уже существующем «Качество JPEG: {0} %», `UiLanguage.cs:53`). Обновляется синхронно, без задержки. Подпись «Громкость» остаётся на месте, как просит ТЗ.

### Точные места правки

**1. Новый файл `src/Snapik.App/SoundVolumeCurve.cs`** (по образцу `SoundThrottle.cs`), без единого типа WPF:

```
internal static class SoundVolumeCurve
{
    /// <summary>Амплитуда для MediaPlayer.Volume: ползунок 0..100 по квадрату, поверх него микс звука.</summary>
    internal static double Amplitude(int volume, double gain)
    {
        var level = Math.Clamp(volume, 0, 100) / 100.0;
        return level * level * Math.Clamp(gain, 0, 1);
    }
```

### Причина

Два независимых списка палитр.

- Редактор: `OverlayEditorWindow.Appearance.cs:47-60`, массив `Palettes` из четырёх `PaletteSet` в порядке `standard`, `pastel`, `neon` (`:55-56`), `custom`; ряд в UI это `OverlayEditorWindow.xaml:324-331` (`UniformGrid Columns="4"`, сегмент «Неон» на `:328`). ### Про «волну 0»

Из моего разбора волна 0 **не требуется**: ни одной правки в общих с C файлах у A+D нет. Если Никита всё-таки хочет единый список палитр (вариант 2 в D2), то делать это надо именно волной 0, до старта B и C, и в такой форме:

1. Новый файл `src/Snapik.App/AnnotationPalettes.cs`, куда чистым перемещением (без изменения тела) уезжают `PaletteSet` (`OverlayEditorWindow.Appearance.cs:45`), массив `Palettes` (`:47-60`), `PaletteFor` (`:67-70`), `CustomPalette` (`:72-73`) и `ParseAnnotationPalette` (`:759-760`).
2. Чтобы не переписывать 20 мест вызова (`OverlayEditorWindow.Palettes`, `OverlayEditorWindow.ParseAnnotationPalette` живут в `SmokeTestRunner.cs:84-96`, `HotkeySettingsWindow.xaml.cs:62`, `OverlayEditorWindow.xaml.cs:304-306,635`), новый файл делается **ещё одной частью того же `partial class OverlayEditorWindow`**. Тогда это чистый move, компилятор видит те же имена, диффа в вызывающих ноль, а дорожка C получает `OverlayEditorWindow.Appearance.cs` уже без палитрового блока и наступает только на свои `InspectorViewOf`-места.
3. Ряд в `AppearancePicker` при этом всё равно **оставить именованными `RadioButton`**, иначе ломаются `RunProbe` и смоук, а выигрыш нулевой: сторож из «Тестов» D2 даёт ту же гарантию дешевле.
4. Волна 0 коммитится и пушится в `master` **до** создания worktree под B и C (правило `~/.claude/rules/git-worktrees.md`: ветка уходит от `origin/master`, а не от локального HEAD).

Мой совет: волну 0 в этом раунде не делать. Пункты 1 и 2 полезны сами по себе, но это рефакторинг без единого пользовательского эффекта, а раунд и так несёт девять правок в трёх дорожках.

## Изменение формата (`settings.json`), правило 4 `AGENTS.md`

**Поле `AnnotationPalette`.** Формально набор допустимых значений в этом раунде не расширяется: четвёртое значение `"neon"` появилось ещё в 1.6.0 вместе с `Palettes[2]` (`OverlayEditorWindow.Appearance.cs:55-56`) и уже сегодня пишется в файл редактором. Меняется другое: **у поля два пишущих, и до 1.7.0 второй из них умел писать только три значения из четырёх.** Окно настроек (`HotkeySettingsWindow.xaml.cs:240` → `EdgeStackWindow.xaml.cs:1457`) обрезало `"neon"` до `"standard"` на сеттере `AppearancePicker.SelectedPalette` (`Controls/AppearancePicker.xaml.cs:122`) и переписывало файл при любом нажатии «Сохранить», даже если вкладку «Вид» не открывали. С 1.7.0 окно настроек принимает и пишет `"neon"` наравне с редактором.

Что это значит для порта. `settings.json` версию схемы не поднимает (`SettingsMigration.CurrentVersion` остаётся 2, `SettingsMigration.cs:13`), миграция не нужна ни для громкости, ни для палитры. Файл, написанный 1.7.0 со значением `"neon"`, читается сборкой 1.5.0 как `"standard"` (`ParseAnnotationPalette`, `OverlayEditorWindow.Appearance.cs:759-760`, неизвестное имя падает в стандартную палитру), то есть вниз совместимость сохраняется без потери файла. Mac-порту нужно, чтобы **оба** его экрана выбора палитры (редактор и настройки) знали одни и те же четыре имени в одном и том же порядке `standard`, `pastel`, `neon`, `custom`, и чтобы экран настроек не перезаписывал значение, которого он не показывает.

**Поле `SoundVolume`.** Формат не меняется: тип `int`, диапазон 0..100, дефолт 40 (`HotkeySettings.cs:30`, `SettingsMigration.cs:16`), миграции нет. Меняется **смысл** сохранённого числа: с 1.7.0 оно переводится в амплитуду по квадрату (`level² × gain`, `SoundVolumeCurve.Amplitude`), а не линейно. Значение 100 звучит ровно как раньше, все остальные тише. Это правило поведения по правилу 5 `AGENTS.md`, и Mac обязан взять ту же формулу, иначе один и тот же файл настроек даст на двух платформах разную громкость. Три микса (`0.6` затвор, `0.25` тик, `0.7` «скопировано», `UiSoundService.cs:22-24`) не меняются.

**A1** формата данных не касается вовсе.
