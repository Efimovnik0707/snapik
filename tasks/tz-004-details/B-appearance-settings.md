## 1. Что показал разбор кода

### 1.1. Тем в приложении нет

`ThemeService` (`src/Snapik.App/ThemeService.cs:13-50`) умеет ровно одно: подменить словарь акцента в `Application.Current.Resources.MergedDictionaries` по индексу (`:33-36`). Параметр `theme` принимается и выбрасывается: `CurrentTheme = DefaultTheme` жёстко (`:39`), комментарий в шапке (`:11`) это фиксирует («Only the dark theme exists in this phase»).

`Themes/SnapikTheme.xaml` (160 строк) описывает **светлую** палитру (`PaperColor #FCFBF8`, `PanelColor #FFFFFF`, `InkColor #172033`, `:4-12`), которой в приложении фактически никто не красится: все окна тёмные и красятся своими литералами. Исключение наоборот: стиль `ContextMenu` в том же файле (`:127-158`) захардкожен тёмным (`#171A20`, `#3A424E`, подсветка `#2B3543`, галочка `#71ADFF`).

Ключевая деталь для живого предпросмотра: брашы темы объявлены и читаются через `StaticResource` (`:15-24`, ссылки `:29-30, 36-44, 74, 89-91, 103-107, 118-125`). `StaticResource` разрешается один раз при построении дерева и подмену словаря не замечает. Акцент, наоборот, везде `DynamicResource` (`:55, 66-68, 93, 95, 108-111`), поэтому он и переключается живьём. Любая тема требует перевода этих ссылок на `DynamicResource`.

### 1.2. Акцент

Четыре словаря `Themes/Accents/{Blue,Teal,Violet,Coral}.xaml`, семь ключей в каждом: `AccentColor`, `AccentBrush`, `AccentHoverBrush`, `AccentPressedBrush`, `AccentSoftBrush`, `AccentTextBrush`, `FocusBrush` (`Blue.xaml:7-13`). Все `SolidColorBrush`. Значения (история в `verification.md:366-378`): blue `#2F8CFF`, teal `#2BB3A3`, violet `#8B7CF6`, coral `#FF7A59`. **Ни одно из трёх последних не совпадает с ТЗ B4** (зелёный `#28BE80`, фиолетовый `#AF81FF`, оранжевый `#FF8C42`).

Применяется акцент в двух точках: `EdgeStackWindow.xaml.cs:86` (старт, сразу после чтения настроек, до `InitializeComponent`) и `EdgeStackWindow.xaml.cs:1192` (после успешного `MutateSettings` в `TryApply`). Живьём перекрашивается всё, что читает `DynamicResource`. То есть **механика живого предпросмотра для мастера уже есть**: достаточно позвать `ThemeService.Apply` из обработчика клика, ничего не сохраняя.

Смоук держит инвариант «наборы ключей всех словарей акцента совпадают» (`SmokeTestRunner.cs:164-168`) и проверяет конкретные цвета teal и blue (`:162, :170`).

### 1.3. Где живёт тема и акцент в settings.json

`HotkeySettings.Theme` (`HotkeySettingsWindow.xaml.cs:80`, string, default `"dark"`) и `AccentId` (`:81`, default `"blue"`). Оба поля заведены в 1.2.x заранее (`verification.md:368`).

`Theme` **никто не пишет**: в `OnSave` (`:387-400`) его нет, в `MutateSettings` ленты (`EdgeStackWindow.xaml.cs:1179-1190`) тоже. Значение всегда `"dark"`, и `ThemeService.Apply` его всё равно игнорирует. Добавление тем это дописывание поля в две записи, а не новое поле в формате.

`SettingsVersion` (`:31`), `CurrentSettingsVersion = SettingsMigration.CurrentVersion = 1` (`SettingsMigration.cs:11`). Правило миграции ровно одно, про громкость (`:23-24`). Миграция применяется при чтении и один раз записывается обратно (`:99-106, 166-175`).

### 1.4. Конфликты клавиш: что уже есть

`HotkeyRules.cs` (49 строк) знает три правила: PrintScreen и Pause это сочетания сами по себе (`:16`), модификатор не может стоять на месте клавиши (`:24-25`), разбор `custom:{modifiers}:{vk}` с отсевом мусора (`:35-48`). **Ни чёрного списка системных сочетаний, ни проверки дублей нет.**

Дубль сегодня ловится косвенно и криво: `TryApply` (`EdgeStackWindow.xaml.cs:1173-1176`) снимает обе регистрации и регистрирует заново, вторая `RegisterHotKey` с тем же сочетанием падает Win32 1409, пользователь видит «Эта клавиша уже занята. Освободите её в другом приложении или выберите другую» (`:1202-1203`). Сообщение врёт (занято своим же приложением) и не показывает, какое из двух полей виновато. Плюс защита исчезает, если одна из галочек выключена (`:1175-1176`).

`HotkeyField` (`Controls/HotkeyField.xaml.cs`) проверяет только наличие модификатора (`:125-132`). Состояния ошибки у контрола нет: рамка либо покой `IdleBorder` (`:22, :61`), либо `FocusBrush` в режиме записи (`:60`). Точка для текста ошибки готова: `Caption` уже перезаписывается при отказе (`:130`).

Дефолты: capture `"ctrl-alt-s"` (`:92`) совпадает с ТЗ. `DefaultFullscreenSaveId = "custom:4:44"` (`:21-22`), это Shift+PrintScreen (modifiers 4 = Shift, vk 44 = 0x2C), **а ТЗ требует Ctrl+Alt+Shift+S**. `FullscreenSaveEnabled` по умолчанию `false` (`:19`), то есть «предлагать, не навязывать» наполовину уже так: клавиша выключена, но поле показывает сочетание.

**Хелпер, без которого замену делать нельзя.** Рендереры (`AnnotationCanvas`, `WpfExportImageRenderer`) рисуют через `DrawingContext`, брашу из `DynamicResource` там неоткуда взяться. Нужна одна точка:

```
internal static class AccentPalette   // src/Snapik.App/AccentPalette.cs (новый)
{
    private static readonly Color Fallback = Color.FromRgb(47, 140, 255);
    internal static Color Flat  => Resource<Color>("AccentFlatColor") ?? Fallback;   // первый стоп градиента
    internal static Brush Brush => Resource<Brush>("AccentBrush") ?? new SolidColorBrush(Fallback);
    internal static Pen   Pen(double thickness) => new(Brush, thickness);
    internal static Brush Wash(byte alpha) => new SolidColorBrush(Color.FromArgb(alpha, Flat.R, Flat.G, Flat.B));
}
```

Чтение через `Application.Current?.Resources[...]` с проверкой на `null`: юнит-тесты и часть проб живут без `Application`, падать там нельзя. Фолбэк в **одном** месте, больше ни одного `47, 140, 255` в App не остаётся.

### 3.1. «Стекло»: честная оценка риска

Что требует настоящий Acrylic, по заметке `tasks/tz-002-plan.md:98` (она писалась под этот самый вопрос и остаётся точной):

1. `DwmSetWindowAttribute(DWMWA_SYSTEMBACKDROP_TYPE = 38, DWMSBT_TRANSIENTWINDOW = 3)`, порог сборки Windows ≥ 22621. На Windows 10 его нет, там fallback «тёмная при 85 %».
2. `AllowsTransparency` обязана уйти. Менять её можно **только до создания HWND**, значит переключение темы на «Стекло» и обратно требует пересоздания окна. На ленте висят регистрации горячих клавиш, иконка трея и наблюдатель вставки: пересоздание это не косметика. Это был открытый вопрос `tz-002-plan.md:226` («применяется после перезапуска приложения, нужно ок»), ответа на него до сих пор нет.
3. Скругление переезжает на `DWMWA_WINDOW_CORNER_PREFERENCE = 33`.
4. `Window.Opacity` перестаёт работать: `Opacity = 0` в конструкторе ленты (`EdgeStackWindow.xaml.cs:121`) и анимация `AnimateStackIn` (`:557-563`) переводятся на внутренний `Shell`.
5. Исчезает ручная тень и вместе с ней `Margin="10"`, на который завязаны `PositionAtEdge`, поля хватов и вся арифметика `StripResizeGeometry` (диапазоны 200..380 против 180..360) **вместе с её тестами**.
6. `SizeToContent="Height"` рядом с `WindowChrome` и `GlassFrameThickness="-1"` даёт неустойчивый ремер, нужен прототип. При этом C3 из этого же ТЗ отдельно требует убрать `SizeToContent` ради дёрганья при растягивании, то есть два пункта дерутся за один и тот же код ленты.
7. `WindowChrome.ResizeBorderThickness="0"` обязателен, иначе системная полоса ресайза дерётся с `Thumb`.

Итого настоящее «Стекло» это не тема, а переписывание оконной геометрии ленты с перетряской тестов, пересечённое с C3 и C5 дорожки C. Плюс шесть окон с `AllowsTransparency="True"` (1.7), а не одно.

**Рекомендация: в этот раунд делать B4-4, стекло без Acrylic.** Визуально это ровно то, что нарисовано в эталоне карточки (полупрозрачная серая панель со светлой рамкой), стоит S, ничего не ломает и не блокирует остальные шесть тем. Настоящий Acrylic поднимать отдельным пунктом после того, как C3 и C5 закончены и геометрия ленты устоялась, и начинать с прототипа на одной ленте, а не сразу на шести окнах. Если решение будет «Acrylic сейчас», честнее убрать «Стекло» из шага 4 до готовности: карточка, которая обещает размытие и даёт серую заливку, хуже, чем шесть карточек вместо семи.

### 3.3. D1: где и как валидировать

**Правила в `HotkeyRules` (новое):**

`IsSystemReserved(uint modifiers, ushort virtualKey)`
- любой `modifiers` с битом Win (8) даёт «зарезервировано» (покрывает Win+любая и Win+Shift+S);
- Ctrl|Alt + Delete (0x2E);
- Alt + Tab (0x09);
- Alt + F4 (0x73);
- Ctrl + Escape (0x1B);
- `modifiers == 0 && virtualKey == 0x2C`, то есть голый PrintScreen: на Win11 его забирает Snipping Tool;
- голый Pause (0x13) остаётся разрешённым;
- macOS-ветка (Cmd+Shift+3/4/5, Cmd+Tab, Cmd+Space) в Windows-коде не пишется, но список фиксируется комментарием рядом с функцией, чтобы порт перенёс его вместе с ней.

`SameGesture(idA, idB)` сравнивает разобранные `(modifiers, virtualKey)`, а не строки: пресет `"print-screen"` (`HotkeySettings.Choices:112`) и `"custom:0:44"` это одно сочетание. Разбор идёт через `HotkeySettings.Find(id).Gesture`.

**Живьём в `HotkeyField`.** В `RecordKey(Key, uint)` (`:119-138`) после проверки модификатора добавляются два отказа: системное сочетание (`Caption` = «Это сочетание занято Windows») и конфликт с соседним полем (`Caption` = «Уже занято»). В обоих случаях рамка красная `#FF6B6B` (в тон существующему `ErrorText` `#FF9B95`), запись продолжается, старое сочетание остаётся. Это третье состояние рамки помимо `IdleBorder` (`:22`) и `FocusBrush` (`:60`).

О соседях контрол узнаёт не сам: новое свойство `IReadOnlyList<HotkeyField> ConflictsWith`, окно связывает поля в конструкторе (`HotkeySettingsWindow.xaml.cs:287-288`). Мастеру соседнего поля нет, ему нужен список уже занятых идентификаторов из настроек (`IReadOnlyList<Func<string>> ReservedIds`), чтобы шаг 2 не дал назначить то, что уже стоит на «весь экран».

**В блоке сохранения.** `HotkeySettingsWindow.OnSave` (`:380-406`) до вызова `TryApply`: если обе клавиши включены и `SameGesture(CaptureField.HotkeyId, FullscreenField.HotkeyId)`, оба поля краснеют, `ErrorText` показывает «Одно сочетание на два действия. Поменяй одно из них.», `DialogResult` не ставится. Это перекрывает случай, когда сочетание было записано раньше, чем соседнее поле его заняло, и снимает зависимость от Win32 1409 (`EdgeStackWindow.xaml.cs:1202-1203`), который срабатывает только при обеих включённых галочках и врёт про чужое приложение.

**Дефолты.** `HotkeySettings.Default.CaptureId` остаётся `"ctrl-alt-s"`. `DefaultFullscreenSaveId` меняется `"custom:4:44"` → `"custom:7:83"` (Ctrl+Alt+Shift+S; 7 = Alt|Control|Shift, 83 = 0x53 = S). Меняется только значение по умолчанию, файл с уже записанным ключом читается как записан.

### 3.4. E5: палитра «Своя»

**Спектр (минимально достаточная реализация в WPF, без сторонних библиотек).** Новый `Controls/ColorSpectrum`, два элемента:
- hue-полоса, вертикальный `Rectangle` шириной 16, залитый `LinearGradientBrush` из семи стопов (0, 60, 120, 180, 240, 300, 360 градусов: `#FF0000 #FFFF00 #00FF00 #00FFFF #0000FF #FF00FF #FF0000`), маркер горизонтальная черта;
- квадрат S/V 160×160 в `Grid` из двух слоёв: нижний `LinearGradientBrush` слева направо `#FFFFFF` → чистый hue (пересобирается при смене hue), верхний `LinearGradientBrush` сверху вниз `#00000000` → `#FF000000`. Маркер кружок 12 px, белый штрих поверх чёрного.

Мышь: `CaptureMouse` на нажатии, `x / ширина` это насыщенность, `1 - y / высота` это яркость, значения клампятся в 0..1. Конверсия в `Imaging/ColorConversion.cs` (`HsvToRgb`, `RgbToHsv`, чистые функции, покрываются xUnit round-trip, серые и краевые оттенки отдельными кейсами, кириллица тут ни при чём, но файл всё равно UTF-8).

**HEX.** Поле `ColorHex` и `ApplyHex` (`Appearance.cs:422-431`) уже есть, расширяется до двусторонней синхронизации со спектром: ввод в HEX двигает маркеры, движение маркеров пишет HEX.

**Пипетка.** Кнопка рядом с HEX. Захват пикселя: `GetDC(IntPtr.Zero)` плюс `GetPixel(hdc, x, y)` плюс `ReleaseDC` из `gdi32`, координаты курсора через `GetCursorPos` (физические пиксели, приложение per-monitor DPI aware). Один вызов на движение, работает поверх любого окна и на любом мониторе. Альтернатива через существующий захват (`CaptureOverlay` плюс `DesktopFrame`) дороже: она снимает весь экран ради одного пикселя и требует отдельной арифметики на смешанном DPI. Рекомендую `GetDC(0)`/`GetPixel`.

Режим: клик по кнопке ставит прозрачный оверлей поверх всех мониторов (по образцу `CaptureOverlay`), курсор `Cross`, при движении HEX и превью обновляются живьём, клик фиксирует цвет, Esc отменяет и возвращает прежний. Поповер редактора на время пипетки прячется, иначе пипетка возьмёт цвет собственной панели.

**12 слотов.** Ряд из 12 кружков под спектром, разметка та же, что у обычной палитры (`BuildSwatches`, `Appearance.cs:136-160`). Правило: зафиксированный цвет встаёт в первый слот, остальные сдвигаются; цвет, который уже есть в ряду, поднимается наверх, а не дублируется; ряд короче 12 дорисовывается пустыми ячейками. Хранение: новое поле `CustomPaletteColors` (string[] из hex, по умолчанию пустой массив), абзац «Изменение формата» в разделе 5.

`PaletteSet` для «Своей» это запись с `Id = "custom"` и пустыми массивами: `Colors` и `Quick` подставляются из `CustomPaletteColors` во время построения, а не лежат константой (`Palettes` статический, `Appearance.cs:43`). Значит нужен метод `PaletteFor(settings)` рядом с `ParseAnnotationPalette` (`:541-542`), а не мутируемое статическое поле.

## 5. Изменение формата (черновик абзацев для `tasks/verification.md`)

> **Изменение формата.** В `settings.json` поле `Theme` (string, по умолчанию `"dark"`, заведено в 1.2.x и до сих пор никем не писалось) начинает принимать семь значений: `dark`, `light`, `glass`, `night`, `sunset`, `sea`, `dawn`. Неизвестное значение гасится в `dark` тем же способом, что и неизвестный акцент (`ThemeService.Normalize`), поэтому старый файл с `"dark"` читается как прежде, а файл, записанный новым билдом, читается старым билдом без ошибок (старый билд тему всё равно игнорирует). `SettingsVersion` не меняется: переписывать в старых файлах нечего. macOS-порту нужен тот же список значений и то же правило гашения.

> **Изменение формата.** Значения четырёх акцентов меняются, идентификаторы остаются: `blue` `#2F8CFF` (без изменений), `teal` `#2BB3A3` → `#28BE80` (в интерфейсе называется «зелёный»), `violet` `#8B7CF6` → `#AF81FF`, `coral` `#FF7A59` → `#FF8C42` («оранжевый»). Миграция не нужна: в файле лежит идентификатор, а не цвет. Добавлены четыре градиентных акцента: `blue-violet` (`#2F8CFF` → `#AF81FF`), `orange-rose` (`#FF8C42` → `#FF4D6D`), `green-cyan` (`#28BE80` → `#00C8DC`), `amber-pink` (`#FFBE2E` → `#FF79B7`), все под углом 135°. Стопы градиентов в `settings.json` **не пишутся**: файл несёт только `AccentId`, значения живут в словарях `Themes/Accents/*.xaml`, чтобы Windows и macOS не разъезжались по цветам. Во всех восьми словарях появился ключ `AccentFlatColor`: у сплошных он равен `AccentColor`, у градиентных это первый стоп, и его берут места, которым нужен `Color`, а не `Brush` (альфа-смеси, экспортный PNG).

> **Изменение формата.** В `settings.json` добавлен ключ `CustomPaletteColors` (массив строк hex, по умолчанию пустой, не длиннее 12): сохранённые цвета палитры «Своя». Изменение аддитивное, старый файл без ключа даёт пустой ряд, новый файл читается старым билдом (лишний ключ игнорируется). Невалидный hex при чтении выбрасывается, лишние элементы обрезаются. Там же значение `AnnotationPalette` `"neon"` больше не существует: палитра «Неон» заменена на `"custom"` («Своя»). Отдельная миграция не нужна, `ParseAnnotationPalette` гасит неизвестный идентификатор в `standard` (`OverlayEditorWindow.Appearance.cs:541-542`); тот, кто сидел на «Неоне», при первом открытии поповера увидит «Стандартную». macOS переносит ключ, ограничение длины и правило гашения.

> **Изменение формата.** Значение по умолчанию у `FullscreenSaveId` меняется с `"custom:4:44"` (Shift + Print Screen) на `"custom:7:83"` (Ctrl + Alt + Shift + S), как требует ТЗ №3 D1. Формат идентификатора не меняется. Файл, где ключ уже записан, читается как записан; новый дефолт получают только чистая установка и файл без ключа. `FullscreenSaveEnabled` остаётся `false` по умолчанию: клавиша предлагается чипом, а не навязывается.

### 6.1. Дорожка A (онбординг)

Контракт на шаг 4:

```xml

                           ThemeChanged="OnAppearanceChanged"
                           AccentChanged="OnAppearanceChanged" />
```

- Контрол сам ничего не сохраняет и ничего не читает из настроек. Мастер выставляет `Appearance.SelectedTheme` и `Appearance.SelectedAccent` при построении шага и забирает их в кандидата настроек при «Далее» и «Начать» (`OnboardingWindow.xaml.cs:205` уже строит кандидата для `TryApply`).
- Живой предпросмотр контрол делает сам: обработчик клика зовёт `ThemeService.Apply(theme, accent)`. Мастеру ничего делать не нужно, **но** окно мастера перекрасится только в той мере, в какой оно читает цвета через `DynamicResource`. Пункт B4-2 обязан пройти по `OnboardingWindow.xaml` (там 9 вхождений `#2C3746`, 4 `#1B212B`, 3 `#33404F`, 2 `#171B22`), иначе на «Море» у мастера перекрасятся кнопки и не перекрасится фон.

- Размеры: полоса контента 520 px при ширине окна 620. Высота блока «Тема» 122 (подпись 20 плюс галерея 94 плюс отступ), блока «Цвет» 64, примера 58. Итого 244 плюс заголовки шага.

Оба захода точечные, но конфликтные по файлу: **B делает их последним коммитом, после того как A закончила перерисовку мастера.**
