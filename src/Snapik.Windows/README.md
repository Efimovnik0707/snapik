# Snapik.Windows

Windows-only transport adapters for a prepared immutable export. The application layer maps `PreparedExport` to:

```csharp
new PreparedPastePackage(
    prepared.Manifest.ExportId,
    prepared.GetImagePathsInOrder(),
    prepared.Manifest.PromptText);
```

`PasteCoordinator` supports one composite `CF_HDROP` + Unicode text clipboard object and a staged image/text sequence. Staged PNGs expose the registered `PNG` bytes plus standard `CF_DIB` and auto-convertible `CF_BITMAP` representations. Every retry checks the Windows clipboard sequence immediately before WPF/OLE writes and stops when another application has already changed it. WPF opens the clipboard internally, so this is a best-effort race guard rather than a native atomic compare-and-swap; the coordinator also checks the resulting sequence after each write. `SetDataObject(copy:true)` flushes persistent data before success. If Snapik becomes owner but that flush is temporarily blocked, the service detects its own `DataObject` and retries only `Clipboard.Flush`, while its dedicated STA dispatcher remains able to service OLE messages. The coordinator captures the foreground top-level window and focused child control and rechecks both around each shortcut. When Windows does not expose a focused child handle, this guard falls back to top-level window identity.

Every foreground application except Codex Desktop uses an opt-in intercepted path because a physical Ctrl+V or Alt+V over a multi-image package must not receive the composite object as-is. When the application predicate confirms Snapik clipboard ownership, a usable foreground target, a paste gesture (Ctrl+V or Alt+V), and that the target does not match the `CodexDesktop` profile, `WindowsPasteIntentObserver` suppresses that physical V keydown and its repeats regardless of which modifier accompanies it. `CompleteSequentialAsync` (formerly `CompleteClaudeAsync`, kept as a thin wrapper) publishes each image separately with the registered `PNG` clipboard format plus standard `CF_DIB`/`CF_BITMAP` representations, dispatches one guarded paste per image using the same gesture the user physically pressed (Ctrl+V or Alt+V) with a settlement delay between writes (700 ms by default, 1200 ms after an Alt+V image so a terminal has time to accept it), then publishes immutable Unicode prompt text and dispatches a final guarded Ctrl+V — terminals that use Alt+V for images still expect Ctrl+V for text. Codex Desktop keeps its original single-shortcut `CompleteAsync` path against the composite clipboard object. Injected keystrokes are identified by `LLKHF_INJECTED` and remain outside interception; Snapik's own synthetic paste keystrokes are marked injected so the hook never suppresses them. Without an interceptor predicate and an event subscriber, the observer remains passive.

The persistence and ownership behavior follows Microsoft's [`Clipboard.SetDataObject`](https://learn.microsoft.com/dotnet/api/system.windows.clipboard.setdataobject?view=windowsdesktop-10.0) and [`Clipboard.Flush`](https://learn.microsoft.com/dotnet/api/system.windows.clipboard.flush?view=windowsdesktop-10.0) contracts. Image formats follow the Win32 [standard and synthesized clipboard formats](https://learn.microsoft.com/windows/win32/dataxchg/clipboard-formats). Chromium's Windows clipboard implementation reads its registered PNG representation from the complete [`HGLOBAL` byte range](https://chromium.googlesource.com/chromium/src/+/master/ui/base/clipboard/clipboard_win.cc#1191); the Claude-specific object therefore uses a fixed-size stream and persists it before dispatch. Interception follows the documented [`LowLevelKeyboardProc`](https://learn.microsoft.com/windows/win32/winmsg/lowlevelkeyboardproc) nonzero return contract and [`LLKHF_INJECTED`](https://learn.microsoft.com/windows/win32/api/winuser/ns-winuser-kbdllhookstruct) flag. Tests query the WPF `DataObject` through COM `IDataObject` directly to verify the complete PNG `TYMED_HGLOBAL` is byte-for-byte identical to the source file and independently decodable, without publishing anything to the system clipboard.

Built-in profiles are deliberately `Unverified`. `UnobservableAcceptanceObserver` waits only for a calibrated delay and returns `NotObservable`; its successful completion produces `CompletedUnverified`, never `CompletedVerified`. A later UI Automation observer may return `Accepted` only when it observes the relevant attachment or text state. Safe resume is offered only for a contiguous prefix of observed image acceptances. After any unobservable step the user must inspect the draft before retrying.

No profile may contain Enter. `WindowsInputInjector` rejects Enter again at the native boundary. Before injecting, it waits up to 750 ms for Ctrl, Shift, Alt, Windows, and the gesture key to be physically released, so the global trigger cannot leak modifiers into the target shortcut. It never synthesizes key-up for a key the user is holding. `SendInput` can fail across Windows integrity levels and does not itself prove that the target accepted content.

The installed-machine process inventory on 2026-09-08 showed the Codex desktop package using process name `ChatGPT`, Claude desktop and CLI using `claude`, Codex CLI using `codex`, and no active `WindowsTerminal` process. Profiles are selectable and immutable; the settings UI may create a user-specific `TargetProfile` for another terminal host and gestures. A selected profile identifies the intended host, but a shared host process cannot prove which CLI is running in its current terminal tab.

Automated tests use fakes and never open the live clipboard, inspect UI, or inject input. Real compatibility remains unverified until the manual P1 matrix is completed in throwaway drafts for each exact app/version.

A `CompletedUnverified` result from `CompleteSequentialAsync`/`CompleteAsync` does not by itself rotate the Snapik session. `EdgeStackWindow.RepublishPackageForReuseAsync` (application layer, `src/Snapik.App`) republishes the same immutable image paths and prompt text through `SetPackageGuardedAsync`, using the just-completed step's receipt as the expected sequence, so the composite package — not just the trailing text write — stays the current clipboard owner and can be pasted into another application without a new capture in between. If the guard rejects the republish because another application already changed the clipboard, Snapik leaves that foreign clipboard untouched and reports the package as displaced. The session is not rotated at all: the pasted captures stay in the strip with a sent flag, the next capture rebuilds the package out of the captures that are still waiting (`SaveAndCopyCommittedPackageAsync`), and only "clear the strip" archives the session and gives the clipboard back. What the completion works on is `_published` — the paths, the text and the capture ids that were actually written to the clipboard — and not `_prepared`, the export the next publication will be built from; the two diverge as soon as a capture is marked sent, removed or reordered.

Some receivers write their own rendering of a just-completed paste back onto the clipboard a moment later — a terminal hosting Claude Code, for example, has been observed replacing the clipboard with text like `[Image #2]Снимок A.\r\n  A1: тест1` (its own placeholder for the pasted image plus the pasted prompt text) right after a per-image paste sequence finishes. That overwrites Snapik's clipboard sequence number, so the next physical Ctrl+V/Alt+V misses the interception predicate (`ownedSeq != intentSeq`) and the receiver's echoed text gets pasted into whatever the user targets next instead of the package. `ClipboardEchoDetector.IsReceiverEcho(ClipboardSnapshot, string promptText)` (this project, no WPF dependency) classifies such a clipboard change as a receiver echo — no `FileDrop`, no image formats (`Bitmap`/`DeviceIndependentBitmap`/`PNG`), and a `[Image #N]`-stripped, whitespace-collapsed text match against the prompt — versus a genuine foreign copy. `EdgeStackWindow` polls the clipboard every 200 ms for `ReceiverEchoWatchWindow` (6 s, extended on every detected echo) after each successful republish; a detected echo triggers another `SetPackageGuardedAsync` republish (logged as `PasteIntent re-armed after receiver echo: from seq X to Y`) so the package keeps matching the predicate, while a non-echo change stops the watch and logs `PasteIntent package displaced by foreign clipboard write` without touching the foreign clipboard.
